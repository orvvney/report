# Технический паспорт проекта

Дата актуализации: 12 ноября 2026 года.

## Назначение и состояние

`report` — локальный отчёт об успешных сделках с квартирами (`Բնակարան`) в Битрикс24. Армянский интерфейс
показывает количество квартир и суммы AMD со статистикой и KPI,
с мгновенными локальными фильтрами по периоду, комплексу, комнатности, площади и цене.
В шапке слева расположен логотип Milon Mining, справа — квадратные кнопки
обновления и меню, в широком виде между ними заголовок `Հաշվետվություն`.
Меню содержит `Բնակարաններ` / `Ավտոկայանատեղիներ`; выбор пока только закрывает
меню и не меняет квартирные данные. Фавикон использует файл логотипа.
Шапка начинается у верхнего края, все внешние блоки занимают полную ширину сайта.
Отступы сверху до логотипа, от логотипа до фильтров, от фильтров до KPI и после
гистограммы до низа одинаковы (20 px в широком виде, адаптивно в узком).
Фильтры и статистика находятся в общей рамке: в широком виде это две равные
половины с центральным разделителем, статистика справа. Она показывает два итога
и круговую диаграмму количества квартир по периоду, комплексу, комнатам,
диапазонам площади или стоимости без новых запросов. Все группировки учитывают
комплекс, комнаты, площадь и стоимость; годовая группировка и её итоговые карточки
считают все загруженные годы, остальные группировки учитывают выбранный период.
Начальная группировка — по комнатам. Легенда имеет заголовки колонок и взаимную
подсветку секторов и строк; годовая легенда сохраняет весь диапазон загруженных лет.
Пирог использует бирюзовую шкалу: чем больше доля, тем темнее сектор.
В итоговых карточках значения стоят над подписями `բնակարան` и `ընդհանուր արժեք`;
общий увеличенный размер чисел подбирается без расширения карточек.
Под этой рамкой находится общий блок KPI количества квартир и суммы продаж:
компактные значения, динамика, линейные мини-графики и рейтинги последних
12 месяцев/всего времени. Ниже с промежутком 24 px расположена гистограмма.
В широком виде KPI имеет высоту 616 px и края, выровненные с верхней рамкой
фильтров и статистики. Содержимое карточек прокручивается внутри общей рамки,
легенды с периодами закреплены снизу, главная сумма показана полностью.
Диалог сделок с переключением периода и страницами по 50 записей открывается
из KPI только в сохранённом узком виде. KPI и детализация учитывают
все применённые фильтры и не зависят от группировки статистики.
Период позволяет выбирать несколько месяцев или кварталов одного года; месяцы
показаны во всплывающем окне сеткой 4×3 с отдельными кнопками выбора всех
доступных месяцев и очистки до одного. Быстрый выбор объединяет текущие/прошлые
месяц и год, последние 12 месяцев и всё время. Широкие половины имеют минимальную высоту
258 px; при переносе дополнительных комнат рамка растёт по содержимому.
Поля площади и стоимости равны по адаптивной ширине. На узком экране фильтры
идут над статистикой и разделены горизонтальной линией.
Текущие календарные периоды ограничены сегодняшним днём. По умолчанию выбраны текущий
год и комплексы Tower/Hills; доступен общий сброс. Квартиры с ошибкой любого
обязательного поля исключаются из статистики и KPI. Остальные типы недвижимости
также исключаются из отчёта. Данные загружаются при открытии страницы и вручную.
Нижняя гистограмма показывает суммы по комнатности, месячные суммы или количество,
с локальным сравнением базового периода KPI. Времени обновления и диалога проблем
в интерфейсе нет; агрегаты `rooms`/`months`, `problems` и `updatedAt` сохранены в API.
Правила расчёта, интерфейс и контракт API описаны
в [отчёте по сделкам](report.md); настройка вебхука и отдельная CLI —
в [инструкции Битрикс24](bitrix24.md).


## Архитектура и технологии

- Vue 3.5.44, Vite 8.3.5, Tailwind CSS 4.3.3; Vue-плагин Vite 6.0.10.
  Статистика и мини-графики KPI рисуются SVG без отдельной библиотеки графиков.
  `App.vue` импортирует `images/logo_milon.png`, `images/filter.png`
  и `images/reset.png`; Vite выпускает их в `/assets/` с хешами имён. Фильтр и сброс используют CSS-маски;
  `index.html` задаёт название вкладки `Milon Mining — Հաշվետվություն`
  и тот же `images/logo_milon.png` как иконку вкладки; сервер перенаправляет
  `/favicon.ico` и `/favicon.png` на хешированный PNG.
  `KpiCard.vue` импортирует `building.png` и `wallet.png` как изображения,
  с нейтральным цветом через CSS-фильтр.
- Сервер использует встроенный `node:http`, интеграция — CommonJS,
  встроенные `fetch` и `node:util.parseEnv`. Для API переиспользуется клиент CLI.
  Клиент последовательно отправляет запросы одного портала с интервалом начала
  минимум 200 мс; очередь общая для обновлений и вкладок внутри процесса.
  Сделки читаются с `start: -1`, явным `select` и фильтром воронки/стадии.
  Пакеты объединяют чтение границ выборки и продолжения диапазонов ID без `total`.
  При транспортной ошибке выполняются до трёх повторов с паузой 2 секунды.
  Подробности — в [инструкции интеграции](bitrix24.md).
- `src/report/filter.cjs` переиспользуется сервером и браузером: точные десятичные
  сравнения и суммы через `BigInt`, фильтрация и построение агрегатов. Vite собирает
  CommonJS из `src/report/` через `build.commonjsOptions`; новой зависимости нет.
  `period.cjs` рассчитывает календарные диапазоны до сегодня по Еревану,
  первую дату и доступные годы по допущенным квартирам, согласует сохранённый
  выбор месяцев/кварталов, преобразует относительный быстрый выбор в эффективный
  календарный период без изменения ручной памяти. `filter.cjs` объединяет
  выбранные диапазоны через
  `dateRanges`, сохраняя пересечение с остальными фильтрами; пустой массив
  исключает все сделки, отсутствие условия сохраняет прежний расчёт.
  `amount-input.cjs` группирует цену без потери точности, `complex.cjs` проверяет
  метаданные комплекса. `RangeInputs.vue` переиспользует поля диапазонов и даты;
  `MonthPicker.vue` открывает нативный popover месяцев мышью, клавиатурой и касанием.
- `src/report/kpi.cjs` рассчитывает итоги, базовые диапазоны, рейтинги и точную
  динамику с десятичными коэффициентами `BigInt`, формирует временные ряды
  и текущую/сравниваемую выборки сделок. Компактный форматтер округляет только
  отображение; `fullKpiAmount` форматирует полное главное значение до сотых без потери
  точности. Общий `filterDeals` используется статистикой, KPI и детализацией.
  `src/report/kpi-axis.cjs` рассчитывает точную десятичную шкалу мини-графиков
  и позиции подписей выбранного периода. `KpiCard.vue` хранит независимые тип
  и раскрытие рейтинга, `KpiChart.vue` рисует адаптивные линии SVG с доступными
  точками, `KpiDealsDialog.vue` отображает локально
  отсортированную таблицу и пагинацию. `App.vue` передаёт единые применённые
  фильтры. API `deals` содержит ID и безопасный URL каждой допущенной сделки;
  открытие диалога, переключение периода и пагинация не создают новых запросов.
- `src/report/statistics.cjs` локально группирует допущенные квартиры после
  `filterDeals`, считает точные суммы и полуоткрытые числовые интервалы через
  `BigInt`. Годовая группировка исключает `date`/`dateRanges`, сохраняя остальные
  фильтры. Вес сектора — количество квартир, независимо от группировки.
  Цвета ранжируются по долям после фильтрации и совпадают у сектора и маркера
  легенды; самая большая доля имеет фирменный цвет `#00a387`.
  `groupCategories` объединяет интервалы площади/стоимости после четырёх
  крупнейших в раскрываемую группу `Այլ`, сохраняя исходные категории и итоги.
  `StatisticsPanel.vue` рисует SVG-пирог, легенду с общими колонками, итоговые
  карточки и немодальный popover группировок; импортирует `statistics.png` через
  Vite. `App.vue` согласует общую рамку с шириной KPI и геометрию карточек/пирога
  с полями фильтров через `ResizeObserver`. Новых зависимостей и изменений API нет.
- `src/report/chart.cjs` содержит общий форматтер сумм `fullAmount`, используемый
  KPI и гистограммой, и сохранённые утилиты шкалы Y/времени.
  `histogram.cjs` считает точные месячные сегменты и шкалу,
  `DealsHistogram.vue` рисует SVG-гистограмму с прокруткой и сравнением.
  Серверный `updatedAt` остаётся в API; повторная выдача кеша не меняет его.
- Данные браузер получает через локальный `/api/report`. Вебхук остаётся на сервере;
  CRM не изменяется. API отдаёт агрегаты, проблемы и минимальный нормализованный
  `deals`, включая `id`, `url` и `complex: tower/hills/null`; фильтры не создают новых запросов. `createReportLoader` хранит в памяти
  экземпляра сервера отчёт на 5 минут и справочники на 24 часа, отдельно для каждого
  вебхука; одновременные загрузки одного источника объединяются. Ручное обновление
  обходит только кеш отчёта. `loadReport` выполняет отдельную холодную загрузку
  для проверки производительности. Постоянного хранилища и авторизации приложения нет.
- В режиме разработки Vite пересобирает клиент при сохранении исходников,
  а существующий HTTP-сервер передаёт сигнал полной перезагрузки через SSE
  `/__dev/events`. `node --watch` перезапускает процесс при изменении загруженных
  серверных модулей. Vite использует `configLoader: 'native'` и читает
  `vite.config.mjs` напрямую: временные модули конфигурации в `.vite-temp`
  не создаются и не вызывают цикл перезапусков `node --watch`. Каталог `dist-dev`
  и его содержимое явно исключены из build watcher: изменения сгенерированных
  assets и HTML не запускают новую сборку, даже если их зарегистрировал сканер Tailwind.
  Новых зависимостей для этого режима нет.
- Jest 30.5.2 запускает unit/API в Node.js и e2e через Playwright 1.64.1/Chromium.
  `serve-handler` 6.1.7 остаётся dev-зависимостью, но сервер его не использует.
- Контейнеризация, CI/CD, линтер и форматтер не настроены.

В `mcp.json` объявлены `chrome-devtools` (`npx -y chrome-devtools-mcp@latest`
с `--isolated`, `--chromeArg=--guest`, `--chromeArg=--new-window`) и `context7`
(удалённый HTTP-сервер `https://mcp.context7.com/mcp`). Для обоих включён
`directTools`. Это инструменты разработки, не зависимости страницы. Ключи доступа
в репозиторий не включаются. Тег `latest` у Chrome DevTools не закрепляет версию;
наличие конфигурации не подтверждает работоспособность MCP-соединения.

## Установка и локальный запуск

Нужны Node.js **22.12.0 или новее**, npm и [настроенный вебхук](bitrix24.md).
Из корня проекта:

```sh
npm ci
npm run build
npm start
```

Откройте `http://127.0.0.1:3000`. Сервер слушает только локальный интерфейс;
остановка — `Ctrl+C`. Для другого порта в macOS/Linux: `PORT=3001 npm start`.
`PORT` берётся из окружения процесса, а не `.env`; допустимы целые числа
от 1 до 65535. Неверный порт или ошибка запуска завершают процесс с ненулевым кодом.
API читает `BITRIX24_WEBHOOK_URL` из окружения либо корневого `.env`.

`npm start` не собирает приложение. После изменения UI выполните `npm run build`
и обновите страницу; после изменения серверного кода перезапустите сервер.
Открытие исходного `index.html` как локального файла не заменяет HTTP-запуск.

Для работы с автоматическим обновлением после сохранения исходников запустите:

```sh
npm run dev
```

Если порт 3000 уже занят обычным сервером, сначала остановите его либо используйте
`PORT=3001 npm run dev`. Правила `PORT` и вебхука те же, что у `npm start`.
Команда сама выполняет первую сборку и только после её успеха начинает слушать
`127.0.0.1`. Сборки пишутся в отдельный `dist-dev/`, поэтому результат `npm run build`
в `dist/` сохраняется. Остановка — `Ctrl+C`.

Успешная повторная сборка отправляет новую ревизию открытым страницам через SSE.
В HTML режима разработки добавляется `EventSource`, который вызывает полную
перезагрузку страницы при смене ревизии. При перезапуске серверного процесса
ревизия также меняется; браузер обновляется после переподключения. Это полная
перезагрузка: выбранный период и фильтры возвращаются к начальным значениям,
а `/api/report` получает снимок по обычным правилам кеша. Перезапуск серверного
процесса очищает оба кеша; пересборка только UI их сохраняет. Ошибка повторной сборки выводится
в терминал и не перезагружает уже открытую страницу; после исправления и успешной
сборки автообновление возобновляется. Ошибка первой сборки препятствует запуску HTTP.

`npm start` продолжает работать без слежения за файлами и без `/__dev/events`.
Запуск `npm run dev` нужен отдельно: наличие команды не переключает уже работающий сервер.

Сервер разрешает `GET`/`HEAD` для `/`, `/index.html` и файлов
`/assets/<имя>.js`, `.css` или `.png` внутри каталога сборки (`dist` у `npm start`,
`dist-dev` у `npm run dev`). PNG отдаются с `Content-Type: image/png`;
исходный каталог `/images/` по HTTP недоступен. Query-параметры не меняют маршрут.
Символические ссылки за пределы каталога сборки блокируются. HTML и assets отдаются
с `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`, `HEAD` — без тела.
Отсутствующий HTML сборки даёт 503 с подсказкой выполнить `npm run build`;
неизвестные пути, методы и недоступные assets — 404. API описан в [report.md](report.md).

Не раздавайте корень проекта стандартным файловым сервером: `.gitignore`
не запрещает чтение локального `.env` по HTTP. Штатный сервер не отдаёт
`.env`, Git, исходники и конфигурацию проекта.

## Проверки и дальнейшая работа

После изменения функционала обязательны тесты вместе с реализацией и полный
`npm test`. E2e setup автоматически создаёт актуальную production-сборку.

```sh
npm run test:install
npm test
```

Состав, результаты и правила тестирования — в [testing.md](testing.md).
Живые проверки интеграции, включая отдельную команду `npm run test:crm-performance`,
описаны в [bitrix24.md](bitrix24.md) и не заменяют автотесты.
Перед сдачей просмотрите diff, проверьте отсутствие секретов и дождитесь
`docs-maintainer` по [правилам документации](documentation.md).

Новая функциональность определяется отдельными задачами. Постоянное хранение,
публичное размещение, авторизация, CI и требования к покрытию пока не определены.
