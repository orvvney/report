# Տուն Էքսպո

## Назначение и навигация

Раздел показывает три набора записей Битрикс24:

- `Հետաքրքրված հաճախորդներ` (`leads`) — лиды Toon Expo без связанных сделок.
- `Անմիջապես գրանցված գործարքներ` (`directDeals`) — сделки Toon Expo без связи с лидом.
- `Հետաքրքրությունից դեպի գործարք` (`deals`) — все сделки, связанные через `LEAD_ID`
  с исходными лидами Toon Expo, независимо от источника самой сделки.

Учитываются все стадии и воронки, процент конверсии не рассчитывается.
`305` — внутренний ID записи справочника источников, а не значение `SOURCE_ID`
карточки. Загрузчик получает соответствующий `STATUS_ID` через `crm.status.list`.
Доступны только записи, видимые владельцу серверного вебхука.

Пункт `Տուն Էքսպո` в общем меню открывает `/#toon-expo` в той же вкладке.
Поддерживаются прямой вход, перезагрузка и история назад/вперёд через `hashchange`.
Возврат в `Բնակարաններ` убирает hash; парковки пока только закрывают меню.
`App.vue` создаёт Expo при первом посещении, затем скрывает/показывает разделы,
сохраняя их локальное состояние. Квартирный отчёт продолжает собственную
начальную загрузку независимо от выбранного раздела.

Общий [`ReportHeader.vue`](../src/ui/ReportHeader.vue) содержит логотип,
`Հաշվետվություն`, обновление и меню. Фактические подзаголовки —
`Կնքված բնակարաններ` для квартир и `Տուն Էքսպո` для Expo (15 px).
Высота шапки от 132 px; её геометрия и отступ до содержимого совпадают
у обоих разделов. Подробности общей шапки — в [report.md](report.md#интерфейс).
Отдельного вступительного блока с заголовком Expo над колонками нет.

## Независимые периоды и таблицы

В [`ToonExpo.vue`](../src/ui/ToonExpo.vue) три равные колонки в указанном выше
порядке с вертикальными разделителями. При ширине окна до 900 px включительно
они расположены вертикально с горизонтальными разделителями. У заголовков
кнопки `!` с теми же подсказками, что у фильтров квартир: наведение, фокус или
нажатие открывают tooltip, уход мыши, потеря фокуса и Escape закрывают его.
Подсказка центрирована под текстом заголовка. Дневных таблиц и отдельных
поясняющих текстов под итогами нет.

У каждой колонки собственные две кнопки периода:

- `Անցած Տուն Էքսպոներ` — дата создания карточки ранее `2026-11-13`;
- `Ներկայիս Տուն Էքսպո` — дата создания карточки от `2026-11-13` включительно,
  без верхней границы.

Даты определяются по `Asia/Yerevan`; граница фиксирована, не сдвигается с текущим
днём. Для лидов используется дата создания лида, для сделок — сделки.
По умолчанию во всех колонках выбран текущий Expo. Выбор применяется локально
без CRM-запросов, меняет только свою колонку. Обновление сохраняет все три
выбора. Лид с любой связанной сделкой исключается до фильтрации периодов и не
возвращается в первую колонку при выборе другого периода третьей.
[`ExpoPeriodFilter.vue`](../src/ui/ExpoPeriodFilter.vue) сохранён, но больше
не подключён к Expo; календарь, месяцы, кварталы и произвольный диапазон недоступны.

Внизу внутри общего `expo-panel` расположен единый блок `Ցանկ`, по умолчанию
свёрнутый. Его счётчик — сумма записей трёх выбранных периодов. Внутри — три
таблицы [`ExpoRecordsList.vue`](../src/ui/ExpoRecordsList.vue) с соответствующими
названиями и отдельными счётчиками; до 900 px включительно они идут вертикально.
Каждая таблица содержит только `Անուն / Ազգանուն` и `Ստեղծման ամսաթիվ`.
Имя ведёт в CRM в новой вкладке с `noopener noreferrer`, ID и заголовок карточки
не отображаются. При отсутствии имени показано `Անունը նշված չէ`.
Дата отображается как `дд.мм.гггг`. Заголовки обеих колонок сохраняются и при
пустой выборке; `Տվյալներ չկան` занимает строку с `colspan="2"`.

Сортировка независима в каждой таблице: по умолчанию дата убывает, при равенстве
убывает ID. Нажатия заголовков переключают сортировку по имени или дате;
имена сравниваются с армянской локалью и учётом чисел. Страницы независимы,
по 25 строк. Смена периода или сортировки сбрасывает только свою страницу.

При первой загрузке запрашивается `/api/toon-expo`; кнопка общей шапки
в Expo и повтор после ошибки используют `?refresh=1`. Пока идёт запрос,
старый снимок скрыт и кнопка обновления заблокирована. При ошибке показано
сообщение с повтором. Таблицы при загрузке/ошибке не показывают старые записи;
после успешного обновления создаются заново с начальными страницами и сортировкой,
выбранные периоды и состояние общего раскрытия сохраняются.
Автоматического обновления по таймеру нет.

## Сервер и HTTP-контракт

Настройка `BITRIX24_WEBHOOK_URL` и запуск совпадают с основным приложением:
[настройка Битрикс24](bitrix24.md#настройка-и-запуск),
[локальный запуск](project.md#установка-и-локальный-запуск).
Новых зависимостей или отдельного вебхука нет.

[`server.js`](../server.js) подключает отдельный `createExpoLoader` из
[`expo-load.cjs`](../src/report/expo-load.cjs). `GET /api/toon-expo`
возвращает полный снимок без серверных фильтров периода. Только `refresh=1`
обходит действующий кеш. Все ответы JSON имеют
`Content-Type: application/json; charset=utf-8` и `Cache-Control: no-store`.

Успешный ответ (200):

```json
{
  "sourceId": "UC_7OQJRN",
  "leads": [],
  "deals": [],
  "directDeals": [],
  "updatedAt": "2026-11-13T10:00:00.000Z"
}
```

`sourceId` — разрешённый `STATUS_ID`, не числовой ID справочника; код в примере
соответствует результату живой диагностики, загрузчик не фиксирует его в коде.
Каждая запись `leads`/`deals`/`directDeals` содержит `id` (положительное безопасное
целое), `title` (строка, при пустом заголовке `#ID`), `date` (`YYYY-MM-DD` по Еревану),
`url` (HTTPS origin портала + `/crm/lead/details/ID/` либо `/crm/deal/details/ID/`)
и `customerName` (строка либо `null`). Записи `deals` дополнительно содержат
`leadId` — ID исходного лида. `updatedAt` — время создания снимка в ISO UTC;
при выдаче из кеша оно не меняется. Полный URL вебхука клиенту не передаётся.

Порядок чтения в [`expo-load.cjs`](../src/report/expo-load.cjs):

1. `crm.status.list` с `filter: { ENTITY_ID: "SOURCE" }`: требуется ровно одна
   запись с `ID = "305"` и непустым строковым `STATUS_ID`. Отсутствие или
   неоднозначность дают ошибку снимка; подстановки числового `SOURCE_ID` нет.
2. Все исходные лиды через `crm.lead.list` с `filter: { "=SOURCE_ID": sourceId }`.
   Поля: `ID`, `TITLE`, `SOURCE_ID`, `DATE_CREATE`, `NAME`, `LAST_NAME`.
3. Все сделки источника через `crm.deal.list` с тем же фильтром и полями
   `ID`, `TITLE`, `SOURCE_ID`, `DATE_CREATE`, `LEAD_ID`, `CONTACT_ID`.
   В `directDeals` остаются только записи с отсутствующим `LEAD_ID`, `null`,
   пустой строкой, `0` или `"0"`. Сделки со сторонним лидом не включаются.
4. Имена прямых сделок дополняются через существующий
   [`addDetails`](../src/bitrix24/details.cjs): основной `CONTACT_ID`, необязательное
   чтение `crm.item.list` с `entityTypeId: 3`. Недоступный контакт или ошибка его
   чтения оставляют `customerName: null`, не исключая сделку и не отклоняя снимок.
5. Для всех исходных лидов группами до 50 ID читаются сделки через
   `crm.deal.list` с `filter: { "@LEAD_ID": ids }`, без фильтра источника,
   стадий и воронок. Поля те же, что у сделок источника. Все связанные сделки
   попадают в `deals`; лиды с хотя бы одной такой сделкой исключаются из `leads`.
   Несколько сделок одного лида сохраняются, поэтому количество сделок может
   превышать количество конвертированных лидов.

Для `leads` и `deals` имя составляется из непустых `NAME`/`LAST_NAME` исходного
лида, а не контакта сделки. Лиды загружаются полностью до исключения связанных.
Сделки источника читаются и при отсутствии лидов.

Для списков лидов/сделок заданы `order: { "ID": "ASC" }`, начальный `start: 0`
и обход всех страниц по `next`. На странице допускается не более 50 записей.
Проверяются положительные ID, строго возрастающий порядок без повторов в каждом
списочном обходе и продвижение `next`. У лидов и сделок выборки источника
проверяется точное совпадение `SOURCE_ID`; у связанных сделок — принадлежность
`LEAD_ID` запрошенной группе. Для нормализуемых записей проверяются ISO-подобная
дата с `T` и возможность преобразования в дату. Ошибка обязательного чтения
или проверки отклоняет весь снимок, частичный успех не выдаётся.
Все вызовы CRM используют существующий клиент чтения
[`client.cjs`](../src/bitrix24/client.cjs); операции записи не добавлены.

Кеш хранится в памяти экземпляра загрузчика 5 минут отдельно по полному URL
вебхука, независимо от кеша квартир. Одновременные обращения к одному источнику
объединяются через `pending`, включая ручные обновления. Возвращается копия снимка.
Перед новым чтением старый кеш очищается; при ошибке обновления он не выдаётся.

| Статус | Тело | Причина |
| --- | --- | --- |
| 500 | `{"error":"CONFIGURATION_ERROR"}` | Ошибка настройки вебхука |
| 502 | `{"error":"CRM_READ_ERROR"}` | Ошибка чтения CRM или проверки снимка |

Ответы ошибок не содержат секретов вебхука, сырых ответов CRM или подробностей исключений.

## Проверки и ограничения

Состав unit/API и браузерных сценариев приведён в
[testing.md](testing.md#проверки-տուն-էքսպո).
По переданным исполнителем результатам полный `npm test` прошёл:
31 набор / 612 тестов, два проекта, 72,6 секунды, exit 0.
Production-сборка входит в этот прогон. Ранее целевые прогоны:
Expo e2e — 13 passed, header/home — 14 passed. `git diff --check` прошёл.
Документатор тесты и сборку повторно не запускал.

Автотесты используют синтетические данные. Живая диагностика только на чтение
подтвердила соответствие внутреннего ID `305` коду `UC_7OQJRN`; числовой
`SOURCE_ID = 305` давал нулевую выборку. Полная живая загрузка после исправления
не выполнялась: полнота трёх наборов под рабочими правами вебхука и получение
имён контактов в полном снимке остаются неподтверждёнными.
