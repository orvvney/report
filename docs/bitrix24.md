# Проверка REST API Битрикс24

Команда `npm run bitrix:check` читает успешные сделки облачного Битрикс24 через
входящий вебхук и показывает результат в терминале. Она не меняет CRM, не сохраняет
выгрузки и не передаёт вебхук в браузер. Тот же клиент используется серверным API
[отчёта по сделкам](report.md); CLI сохраняет отдельный исходный вывод без агрегации
и без отбора по типу недвижимости. Наличие поля `Անշարժ գույքի տեսակ` для CLI
не требуется.

## Настройка и запуск

Нужны Node.js 22.12.0+, npm, доступ к порталу и входящий вебхук с областью `crm`.
Владелец вебхука должен иметь права чтения требуемых сделок.

1. Откройте локальный `.env` в корне проекта. Если его нет после клонирования,
   создайте копию `.env.example`, сохранив существующий `.env`, если он уже есть.
2. Вставьте значение после `BITRIX24_WEBHOOK_URL=` непосредственно в редакторе.
   Это базовый HTTPS URL вебхука с путём `/rest/<ID пользователя>/<токен>/`,
   без имени REST-метода, параметров запроса и фрагмента.
3. Выполните из корня проекта:

   ```sh
   npm run bitrix:check
   ```

Переменная `BITRIX24_WEBHOOK_URL` из окружения процесса имеет приоритет над файлом,
в том числе если она пуста. CLI читает только корневой `.env`; `.env.local` и другие
варианты автоматически не загружаются. Сам CLI не создаёт и не изменяет `.env`.
Для этой команды достаточно встроенных возможностей Node.js; установка npm-пакетов
нужна для [автотестов](testing.md).

`.env` и `.env.*` исключены из Git, кроме пустого `.env.example`.
Не вставляйте вебхук в чат, команды терминала, документацию, fixtures или исходники.
Проверить правила и отслеживаемые пути без чтения секретов можно так:

```sh
git check-ignore -v .env .env.local
git ls-files -- .env '.env.*'
```

В отслеживаемых файлах допустим только безопасный `.env.example`.
Не раздавайте корень проекта файловым HTTP-сервером: `.gitignore` не запрещает
доступ к `.env` по HTTP. Локальный `server.js` и использующие его e2e отдают
только файлы сборки из разрешённых путей и API отчёта; запуск описан
в [техническом паспорте](project.md).

## Какие данные читает команда

Поиск выполняется по точным названиям: воронка **Վաճառք**, стадия **Կնքված**
внутри этой воронки. Три пользовательских поля определяются по заголовкам
метаданных, без заранее заданных кодов.

| Поле CRM | Данные и подпись в выводе |
| --- | --- |
| `Սենյակների քանակ` | Исходное значение одноимённого пользовательского поля |
| Системная сумма `opportunity` | `Ընդհանուր արժեք`, рядом код валюты `currencyId` |
| `Մակերես (մ²)` | Исходное значение одноимённого пользовательского поля |
| `Կնքման ամսաթիվ` | Исходное значение пользовательской даты, без замены системной датой |

Клиент допускает только четыре прикладных REST-метода чтения:

- `crm.category.list` — воронки сделок, `entityTypeId: 2`.
- `crm.status.list` — стадии найденной воронки: `DEAL_STAGE` для ID 0,
  иначе `DEAL_STAGE_<ID>`. Для сделки используется `STATUS_ID`.
- `crm.item.fields` — названия, коды и типы полей с `useOriginalUfNames: 'N'`.
- `crm.item.list` — сделки с фильтром `categoryId`/`stageId`,
  тем же режимом имён полей, `start: -1` и сортировкой по ID.

Для объединения чтений есть `call.batch`: от 1 до 50 структурированных команд
из этого же списка, с `halt: 1`. Вложенные параметры кодируются через
`URLSearchParams`; произвольная строка команды или прямой `call('batch', ...)`
не допускаются. Ошибка любой команды, отсутствие результата или некорректные
карты ответа отменяют пакет без выдачи частичного результата.

Режим `N` используется одновременно в метаданных и списке сделок. Пользовательские
поля выбираются из метаданных по префиксу `ufCrm` и точному заголовку, без
преобразования или угадывания кодов. Это техническое отклонение от рекомендованного
в исходном ТЗ режима `Y`: на проверенном портале с `Y` метод `crm.item.list`
возвращал только выбранные пользовательские поля, пропуская стандартные `id`,
`categoryId`, `stageId`, `opportunity` и `currencyId`. Режим `N` вернул полный набор;
это поведение защищено регрессионным тестом.

`select` перечисляет только `id`, `categoryId`, `stageId`, `opportunity`,
`currencyId` и нужные пользовательские поля. Для отчёта `extraSelect` дополнительно
включает `contactId`. Подъезд, этаж и номер добавляются через `optionalFields`
по исходным кодам `UF_CRM_1776430614152`, `UF_CRM_1686473759`, `UF_CRM_1776254518`.
Сопоставление с метаданными не учитывает регистр и подчёркивания, но в `select`
и при чтении значений используется точный `code`, возвращённый CRM. На проверенном
портале это `ufCrm_1776430614152`, `ufCrm_1686473759`, `ufCrm_1776254518`.
Угадывание camelCase без подчёркивания приводило к пустым значениям.
CLI не запрашивает эти дополнительные данные.
Категория и стадия нужны также для
проверки отбора; ограничения по датам нет. Воронки и поля сначала читаются одним
`batch`, затем определяются стадии найденной воронки. Списки метаданных сохраняют
обычный обход `next`/`start`, если возвращаются несколькими страницами.

Все страницы сделок используют `start: -1`: общий подсчёт отключён,
`total` и `next` не управляют выгрузкой. Первый пакет получает по 50 записей
с начала (`id ASC`) и конца (`id DESC`) выборки. Проверяются длины, порядок,
фильтр и совпадение выбранных полей у перекрывающихся ID; такие записи учитываются
один раз. Промежуток между краями делится максимум на 10 непересекающихся
диапазонов ID. Их страницы объединяются в пакеты; каждый диапазон продолжает
чтение с `>id` последней записи и своей верхней границей `<=id`, пока страница
не станет короче 50. Итог сортируется по ID и проверяется на дубликаты.
Пропуски и неравномерность ID допустимы. Число запросов зависит от распределения
ID, а не только от количества сделок. Пакетный клиент допускает до 50 команд,
но алгоритм диапазонов использует не более 10 продолжений за пакет.

Поведение общее для CLI и отчёта. Ошибка страницы или нарушенная валидация
не превращаются в частичный успех. Обход проверяет полноту неизменяемой выборки,
но несколько REST-запросов не создают транзакционный снимок: одновременные изменения
сделок или прав могут изменить доступные данные во время чтения.

Между началами HTTP-запросов одного портала выдерживается минимум **200 мс**.
Первый запрос свободной новой очереди отправляется сразу; следующий ждёт завершения
предыдущего и истечения интервала от его начала. Очередь общая для всех клиентов
одного HTTPS origin внутри процесса Node.js; отдельные процессы сервера и CLI
не координируются. Это отличается от ключа кеша отчёта, который учитывает полный
вебхук и не смешивает разные права одного портала.

Каждая отправленная попытка имеет таймаут **15 секунд**, включая тело ответа;
ожидание очереди в него не входит. При сетевом отказе, таймауте, ошибке HTTP/REST,
некорректном JSON или транспортной структуре ответа выполняются до **трёх
дополнительных попыток**. Перед каждой — пауза **2 секунды после ошибки**; очередь
может увеличить ожидание. Пауза не занимает очередь. Ошибка подкоманды даже внутри
HTTP 200 повторяет пакет целиком, без использования его частичного результата.
Всего для одного запроса или пакета максимум четыре попытки, а не четыре на каждую
команду. При успехе повторы прекращаются. Проверки предметных данных — ID, порядка,
фильтра, уникальности метаданных — не повторяют уже успешный транспортный запрос.
Ошибки локальной настройки также не повторяются. HTTP-редиректы запрещены.

В сервере работают [кеши отчёта и справочников](report.md#кеширование).
CLI каждый раз читает CRM заново. Общего таймаута отчёта в 3–4 секунды нет:
порог замера средней скорости не ограничивает длительность отдельной загрузки
и не отменяет повторы.

Контракты API: [batch](https://apidocs.bitrix24.com/settings/how-to-call-rest-api/batch.html),
[crm.item.list](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html).

Серверный отчёт получает справочники через `getMetadata` с
`additionalFields: [PROPERTY_TYPE, COMPLEX]` для полей `Անշարժ գույքի տեսակ`
и `Համալիր`. Метаданные сохраняют `items`/`isMultiple`; оба одиночных списка
проверяются до кеширования, даже при пустой выборке. Проверенные справочники
передаются в `getDeals(call, { metadata })`, который включает оба поля в `select`.
Для комплекса динамически разрешаются `Milon Tower` и `Milon Hills`; похожее
поле `Նախընտրելի թաղամաս` не используется. `Milon Plaza` и другие значения
нормализуются в `complex: null`, не меняя базовый допуск квартир и список проблем.
Они не проходят активный клиентский фильтр из Tower/Hills. Ошибки самого поля
или нужных вариантов дают безопасный HTTP 502 без частичного отчёта.
Обычная CLI продолжает использовать прежние три пользовательских поля
и получает все типы недвижимости. Подробный контракт — в [report.md](report.md).

### Контакты и дополнительные поля таблицы

После строгого допуска квартир [`details.cjs`](../src/bitrix24/details.cjs)
обогащает только их записи. Необязательные метаданные подъезда/этажа/номера
сохраняют `items` и `isMultiple`. Отсутствие такого поля не отменяет отчёт,
неоднозначное сопоставление кода даёт безопасную ошибку метаданных.
Подъезд на проверенном портале — `enumeration`: ID варианта преобразуется
в подпись `VALUE`, неизвестный ID даёт `null`. Этаж — `integer`, номер — `string`;
значения сохраняются текстом, включая `0` и номера с ведущими нулями.
Коды определяют поле независимо от его названия: фактический title номера —
`Համար checked`, в таблице остаётся заголовок `Համար`.
Варианты списка кешируются с остальными метаданными на 24 часа;
изменения вариантов могут быть не видны до истечения этого кеша.

Для основного контакта используется `contactId`
(системный `CONTACT_ID`), а не все значения `contactIds`.
Уникальные положительные безопасные ID читаются группами до 50:
`crm.item.list`, `entityTypeId: 3`, `filter: { '@id': ids }`,
`select: ['id', 'name', 'lastName']`, `order: { id: 'ASC' }`, `start: -1`.
Каждая группа помещается в одну страницу; повторяющиеся контакты нескольких
сделок не запрашиваются заново в пределах снимка. Группы выполняются последовательно
через существующий клиент и его общую очередь/повторы.

Пустой, удалённый, недоступный или не прочитанный контакт даёт `customerName: null`.
Некорректный ответ группы, посторонние/повторяющиеся ID или неожиданный `next`
не присваивают имена сделкам этой группы. Такие необязательные данные не отменяют
полную выборку сделок; UI использует ссылку `Գործարք №ID`.
Ошибка чтения самих сделок по-прежнему отменяет отчёт с безопасным 502.
Имя/фамилия и дополнительные строковые поля входят в общий кеш отчёта на 5 минут,
кнопка перечитывает их вместе со сделками; отдельного долгого кеша контактов нет.
Отсутствие подъезда, этажа или номера не меняет допуск квартиры.

Контракты сверены с официальными описаниями
[crm.item.list](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html)
и [контактов CRM](https://apidocs.bitrix24.com/api-reference/crm/contacts/index.html).
Текущая реализация использует уже принятые универсальные методы интеграции;
отдельная живая проверка новых контактных запросов в этой задаче не выполнялась.

Живая проверка дополнительных полей прочитала метаданные и сделки, выполнила
строгий допуск и обогащение: у всех 486 допущенных квартир заполнены `entrance`,
`floor` и `number` (486/486 для каждого поля). Метаданные подтвердили типы
`enumeration` с 8 вариантами, `integer` и `string` соответственно. Вывод содержал
только счётчики и коды полей без клиентов, ID сделок и значений квартир.
Контакты при этой проверке не читались; отдельная проверка отображения живых
данных в браузере не выполнялась. Это состояние доступной выборки на момент
проверки, а не постоянное ожидаемое количество квартир.

## Результат и диагностика

При успехе выводятся идентификаторы воронки и стадии, коды и типы пользовательских
полей, полное количество доступных сделок и до пяти первых примеров по ID.
Значения сохраняются как в API: без округления, конвертации валют, изменения
часового пояса и расшифровки элементов списков. Пустая строка, `null` и отсутствующее
значение обозначаются `не заполнено`; ноль сохраняется.

Код завершения 0 означает, что все страницы прочитаны. Пустая выборка также даёт
код 0, количество 0 и сообщение `Сделок не найдено`.

Код 1 означает ошибку:

- Отсутствующая или неверная настройка: заполните `.env` корректным базовым URL.
  Сетевые обращения до проверки настройки не выполняются.
- Воронка, стадия или поле не найдены либо неоднозначны: диагностика показывает
  проблемное название и кандидатов. Сверьте точные названия и права в CRM.
- Отказ доступа или авторизации: проверьте действительность вебхука, область `crm`
  и права владельца.
- HTTP/REST-ошибка, сеть, таймаут или неверная структура ответа: диагностика
  указывает метод и безопасную причину. При лимите запросов повторите позже.
- Ошибка страницы, неверная пагинация метаданных, нарушенный фильтр или порядок
  сделок: частичная загрузка не выдаётся за успешную.

Необработанные сетевые исключения и тексты ошибок API не печатаются.
URL и токен вебхука скрываются также при отражении в выводимых данных.

## Устройство и границы проверки

- [`config.cjs`](../src/bitrix24/config.cjs) — чтение окружения, проверка URL,
  сокрытие секрета.
- [`client.cjs`](../src/bitrix24/client.cjs) — разрешённые методы, общая очередь
  запросов портала, безопасные пакеты, HTTP, таймаут и ошибки.
- [`deals.cjs`](../src/bitrix24/deals.cjs) — поиск метаданных, пакетная пагинация,
  проверка отбора и форматирование результата.
- [`bitrix-check.cjs`](../scripts/bitrix-check.cjs) — исполняемая CLI и коды выхода.
- [`report-performance.cjs`](../scripts/report-performance.cjs) — отдельные живые
  замеры полной загрузки отчёта без вывода записей CRM.

Автоматические проверки используют искусственные данные, их состав и результаты
описаны в [testing.md](testing.md).

Живая проверка 21 октября 2026 года подтвердила критерий К6: `npm run bitrix:check`
завершилась кодом 0 и прочитала 503 доступные сделки на 11 страницах. Целевая воронка
и стадия найдены; типы пользовательских полей — `integer`, `double` и `date`, валюта
суммы — AMD. Это результат на момент проверки, а не постоянное ожидаемое количество.

Независимый ручной вызов метода чтения `crm.deal.list` подтвердил количество,
первые пять ID и четыре поля с валютой. Даты совпали точно. Суммы численно совпали,
хотя `crm.item.list` возвращал JSON-число, а `crm.deal.list` — строку с дробными
нулями. CLI сохраняет исходные значения `crm.item.list`, без такой нормализации.
При той ручной сверке `crm.deal.list` ещё не входил в клиент. Теперь allowlist
`client.cjs` дополнен только методами чтения `crm.lead.list` и `crm.deal.list`
для [раздела «Տուն Էքսպո»](toon-expo.md). Они используют тот же вебхук
`BITRIX24_WEBHOOK_URL` и права чтения CRM; квартирная CLI сохраняет прежнюю выборку.
Для Expo `crm.status.list` разрешает внутренний ID записи источника `305` в
`STATUS_ID`; именно этот код используется в `SOURCE_ID` карточек. Живая
диагностика только на чтение показала `UC_7OQJRN`; числовой `SOURCE_ID = 305`
давал нулевую выборку. Полная живая загрузка трёх наборов после исправления
не выполнялась. Контракт выборок и границы проверки — в [toon-expo.md](toon-expo.md).

После настройки выполните команду и сверяйте найденные метаданные, количество
и примеры с CRM под правами владельца вебхука. Команда видит только доступные ему
записи и не доказывает отсутствие скрытых правами сделок. При пустой выборке
чтение значений четырёх полей на реальных сделках остаётся непроверенным.
Не сохраняйте реальные ответы в тесты или документацию.


## Проверка отчёта с рабочим порталом

22 октября 2026 года **до введения отбора квартир** живой `GET /api/report`
через `npm start` вернул 200:
год 2026, пять комнатных категорий, 12 месяцев, 472 включённые сделки
в комнатном графике, 224 в месячном и 31 уникальную проблемную сделку.
Это снимок доступной выборки на момент проверки, не константы или ожидания тестов.
Реальные записи не сохранялись. Независимая сверка всех итоговых сумм не выполнялась.

## Живая проверка скорости отчёта

После настройки вебхука выполните отдельную команду:

```sh
npm run test:crm-performance
```

Она не входит в `npm test` и обращается к рабочей CRM. Сначала `loadReport`
выполняет пять независимых полных загрузок без кеша. Время включает метаданные,
все страницы, сеть, очередь, агрегацию, штатные повторы и паузы после ошибок.
Прогрева и исключения выбросов нет; первый неуспешный ответ завершает проверку.
Среднее всех пяти успешных загрузок должно быть **не более 4000 мс**
до округления. Затем `createReportLoader` отдельно измеряет холодную загрузку,
попадание в кеш отчёта и принудительное обновление сделок с действующими
справочниками. Для кеша требуется ноль CRM-запросов, для обновления — новые запросы
сделок без команд метаданных. Код 0 означает успех обеих проверок, иначе код 1.

Вывод содержит только длительности, локальные статусы, количество HTTP-запросов,
команд CRM и команд метаданных, а также сводку. Записи CRM и URL вебхука не печатаются.
HTTP-пакет считается одним запросом, его подкоманды учитываются отдельно.

31 октября 2026 года итоговая серия завершилась `PASS`: пять полных загрузок
вернули 200, каждая использовала **5 HTTP-запросов и 19 команд CRM**.
Длительности — **1235, 1198, 1157, 1241, 2459 мс**; округлённое среднее —
**1458 мс**, минимум — 1157 мс, максимум — 2459 мс. Исходная серия перед изменением
использовала по 5 HTTP-запросов: 1373, 1221, 1331, 1229, 2437 мс,
со средним 1518 мс. Эти короткие серии не доказывают устойчивое процентное ускорение.

Дополнительная проверка кеша также завершилась `PASS`:
