# Проверка REST API Битрикс24

Команда `npm run bitrix:check` читает успешные сделки облачного Битрикс24 через
входящий вебхук и показывает результат в терминале. Она не меняет CRM, не сохраняет
выгрузки и не передаёт вебхук в браузер. Тот же клиент используется серверным API
[отчёта по сделкам](report.md); CLI сохраняет отдельный исходный вывод без агрегации
и без отбора по типу недвижимости. Наличие поля `Անշարժ գույքի տեսակ` для CLI
не требуется.

## Настройка и запуск

Нужны Node.js 22.12.0+, npm, доступ к порталу и входящий вебхук с областью `crm`.
Владелец вебхука должен иметь права чтения требуемых сделок.

1. Откройте локальный `.env` в корне проекта. Если его нет после клонирования,
   создайте копию `.env.example`, сохранив существующий `.env`, если он уже есть.
2. Вставьте значение после `BITRIX24_WEBHOOK_URL=` непосредственно в редакторе.
   Это базовый HTTPS URL вебхука с путём `/rest/<ID пользователя>/<токен>/`,
   без имени REST-метода, параметров запроса и фрагмента.
3. Выполните из корня проекта:

   ```sh
   npm run bitrix:check
   ```

Переменная `BITRIX24_WEBHOOK_URL` из окружения процесса имеет приоритет над файлом,
в том числе если она пуста. CLI читает только корневой `.env`; `.env.local` и другие
варианты автоматически не загружаются. Сам CLI не создаёт и не изменяет `.env`.
Для этой команды достаточно встроенных возможностей Node.js; установка npm-пакетов
нужна для [автотестов](testing.md).

`.env` и `.env.*` исключены из Git, кроме пустого `.env.example`.
Не вставляйте вебхук в чат, команды терминала, документацию, fixtures или исходники.
Проверить правила и отслеживаемые пути без чтения секретов можно так:

```sh
git check-ignore -v .env .env.local
git ls-files -- .env '.env.*'
```

В отслеживаемых файлах допустим только безопасный `.env.example`.
Не раздавайте корень проекта файловым HTTP-сервером: `.gitignore` не запрещает
доступ к `.env` по HTTP. Локальный `server.js` и использующие его e2e отдают
только файлы сборки из разрешённых путей и API отчёта; запуск описан
в [техническом паспорте](project.md).

## Какие данные читает команда

Поиск выполняется по точным названиям: воронка **Վաճառք**, стадия **Կնքված**
внутри этой воронки. Три пользовательских поля определяются по заголовкам
метаданных, без заранее заданных кодов.

| Поле CRM | Данные и подпись в выводе |
| --- | --- |
| `Սենյակների քանակ` | Исходное значение одноимённого пользовательского поля |
| Системная сумма `opportunity` | `Ընդհանուր արժեք`, рядом код валюты `currencyId` |
| `Մակերես (մ²)` | Исходное значение одноимённого пользовательского поля |
| `Կնքման ամսաթիվ` | Исходное значение пользовательской даты, без замены системной датой |

Клиент допускает только четыре прикладных REST-метода чтения:

- `crm.category.list` — воронки сделок, `entityTypeId: 2`.
- `crm.status.list` — стадии найденной воронки: `DEAL_STAGE` для ID 0,
  иначе `DEAL_STAGE_<ID>`. Для сделки используется `STATUS_ID`.
- `crm.item.fields` — названия, коды и типы полей с `useOriginalUfNames: 'N'`.
- `crm.item.list` — сделки с фильтром `categoryId`/`stageId`,
  тем же режимом имён полей и сортировкой `id: 'ASC'`.

Для объединения чтений есть `call.batch`: от 1 до 50 структурированных команд
из этого же списка, с `halt: 1`. Вложенные параметры кодируются через
`URLSearchParams`; произвольная строка команды или прямой `call('batch', ...)`
не допускаются. Ошибка любой команды, отсутствие результата или некорректные
карты ответа отменяют пакет без выдачи частичного результата.

Режим `N` используется одновременно в метаданных и списке сделок. Пользовательские
поля выбираются из метаданных по префиксу `ufCrm` и точному заголовку, без
преобразования или угадывания кодов. Это техническое отклонение от рекомендованного
в исходном ТЗ режима `Y`: на проверенном портале с `Y` метод `crm.item.list`
возвращал только выбранные пользовательские поля, пропуская стандартные `id`,
`categoryId`, `stageId`, `opportunity` и `currencyId`. Режим `N` вернул полный набор;
это поведение защищено регрессионным тестом.

Кроме четырёх полей запрашиваются ID, валюта, категория и стадия для проверки отбора.
Ограничения по датам нет. Первая страница `crm.item.list` читается отдельно.
При наличии `total` и поддержки `call.batch` оставшиеся смещения `start` с шагом
50 объединяются в пакеты до 50 команд; сами пакеты отправляются последовательно.
Проверяются целочисленный неотрицательный `total`, его неизменность, точная длина
каждой страницы, ожидаемый `next` и итоговое количество. Затем проверяются
ID, порядок и принадлежность всех сделок фильтру. Неполнота или изменение `total`
отменяют весь отчёт с безопасной ошибкой 502. Без `total` либо `call.batch`
сохраняется последовательный обход `next`/`start`. Оптимизация действует и в CLI.
Между началами запросов к одному порталу выдерживается минимум **0,2 секунды (200 мс)**.
Первый запрос свободной новой очереди отправляется сразу; следующий ждёт как
завершения предыдущего, так и истечения интервала от его начала. Очередь общая
для всех клиентов одного HTTPS origin внутри процесса Node.js, поэтому ручное
обновление, новая вкладка и другой вебхук того же портала не сбрасывают интервал.
Отдельные процессы сервера и CLI между собой не координируются.

Каждый отправленный запрос имеет таймаут 15 секунд, включая получение тела ответа;
ожидание очереди в него не входит. Ошибка или таймаут освобождают очередь для
следующих вызовов с сохранением интервала.
Автоматических повторов и переходов по HTTP-редиректам нет.
Для 503 сделок с одностраничными метаданными выполняются 5 HTTP-запросов:
3 чтения метаданных, первая страница сделок и один пакет оставшихся 10 страниц.
Это те же 14 логических чтений, но с меньшим числом сетевых обращений.
Интервал и таймаут применяются к HTTP-запросу пакета целиком. Кеширования и общего
таймаута отчёта в 3–4 секунды нет: медленные ответы, дополнительные страницы
и другие загрузки в очереди могут увеличить время.

Контракты API: [batch](https://apidocs.bitrix24.com/settings/how-to-call-rest-api/batch.html),
[crm.item.list](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html).

Серверный отчёт вызывает `getDeals` с дополнительным полем
`Անշարժ գույքի տեսակ`. Параметр `additionalFields` добавляет поле в `select`
и сохраняет его `items`/`isMultiple` для проверки списка и отбора квартир
перед агрегацией. Обычный вызов CLI использует прежние три пользовательских поля
и получает все типы недвижимости. Правила отбора и ошибок отчёта описаны
в [report.md](report.md).

## Результат и диагностика

При успехе выводятся идентификаторы воронки и стадии, коды и типы пользовательских
полей, полное количество доступных сделок и до пяти первых примеров по ID.
Значения сохраняются как в API: без округления, конвертации валют, изменения
часового пояса и расшифровки элементов списков. Пустая строка, `null` и отсутствующее
значение обозначаются `не заполнено`; ноль сохраняется.

Код завершения 0 означает, что все страницы прочитаны. Пустая выборка также даёт
код 0, количество 0 и сообщение `Сделок не найдено`.

Код 1 означает ошибку:

- Отсутствующая или неверная настройка: заполните `.env` корректным базовым URL.
  Сетевые обращения до проверки настройки не выполняются.
- Воронка, стадия или поле не найдены либо неоднозначны: диагностика показывает
  проблемное название и кандидатов. Сверьте точные названия и права в CRM.
- Отказ доступа или авторизации: проверьте действительность вебхука, область `crm`
  и права владельца.
- HTTP/REST-ошибка, сеть, таймаут или неверная структура ответа: диагностика
  указывает метод и безопасную причину. При лимите запросов повторите позже.
- Ошибка следующей страницы, неверный `next`, нарушенный фильтр или порядок
  сделок: частичная загрузка не выдаётся за успешную.

Необработанные сетевые исключения и тексты ошибок API не печатаются.
URL и токен вебхука скрываются также при отражении в выводимых данных.

## Устройство и границы проверки

- [`config.cjs`](../src/bitrix24/config.cjs) — чтение окружения, проверка URL,
  сокрытие секрета.
- [`client.cjs`](../src/bitrix24/client.cjs) — разрешённые методы, общая очередь
  запросов портала, безопасные пакеты, HTTP, таймаут и ошибки.
- [`deals.cjs`](../src/bitrix24/deals.cjs) — поиск метаданных, пакетная пагинация,
  проверка отбора и форматирование результата.
- [`bitrix-check.cjs`](../scripts/bitrix-check.cjs) — исполняемая CLI и коды выхода.
- [`report-performance.cjs`](../scripts/report-performance.cjs) — отдельные живые
  замеры полной загрузки отчёта без вывода записей CRM.

Автоматические проверки используют искусственные данные, их состав и результаты
описаны в [testing.md](testing.md).

Живая проверка 21 октября 2026 года подтвердила критерий К6: `npm run bitrix:check`
завершилась кодом 0 и прочитала 503 доступные сделки на 11 страницах. Целевая воронка
и стадия найдены; типы пользовательских полей — `integer`, `double` и `date`, валюта
суммы — AMD. Это результат на момент проверки, а не постоянное ожидаемое количество.

Независимый ручной вызов метода чтения `crm.deal.list` подтвердил количество,
первые пять ID и четыре поля с валютой. Даты совпали точно. Суммы численно совпали,
хотя `crm.item.list` возвращал JSON-число, а `crm.deal.list` — строку с дробными
нулями. CLI сохраняет исходные значения `crm.item.list`, без такой нормализации.
Метод `crm.deal.list` использовался только при ручной сверке и в клиент не добавлен.

После настройки выполните команду и сверяйте найденные метаданные, количество
и примеры с CRM под правами владельца вебхука. Команда видит только доступные ему
записи и не доказывает отсутствие скрытых правами сделок. При пустой выборке
чтение значений четырёх полей на реальных сделках остаётся непроверенным.
Не сохраняйте реальные ответы в тесты или документацию.


## Проверка отчёта с рабочим порталом

22 октября 2026 года **до введения отбора квартир** живой `GET /api/report`
через `npm start` вернул 200:
год 2026, пять комнатных категорий, 12 месяцев, 472 включённые сделки
в комнатном графике, 224 в месячном и 31 уникальную проблемную сделку.
Это снимок доступной выборки на момент проверки, не константы или ожидания тестов.
Реальные записи не сохранялись. Независимая сверка всех итоговых сумм не выполнялась.

Следующая браузерная загрузка показала предусмотренную ошибку CRM; ручное
обновление успешно восстановило график и 31 проблемную сделку, переключение
на месяцы показало 2026 год. Причина единичного отказа не установлена.
В Chrome открыта реальная карточка сделки и подтверждён путь
`/crm/deal/details/<ID>/`. Изменения в CRM не выполнялись.

При подготовке отбора квартир 22 октября 2026 года чтение `crm.item.fields`
подтвердило единственное поле `Անշարժ գույքի տեսակ` типа `enumeration`,
`isMultiple: false`, с элементами `Բնակարան`, `Թաունհաուս`,
`Ավտոկայանատեղի` и `Հասարակական տարածք`. Код и ID не закреплены в реализации.
Указанные выше количества относятся к прежней выборке всех типов недвижимости.
Независимая сверка итоговых сумм отчёта только по квартирам с CRM не выполнялась.
Автоматические проверки используют искусственные данные.

26 октября 2026 года перед введением интервала две последовательные живые загрузки
отчёта выполнили по 14 запросов за 2,356 и 6,567 секунды; обе вернули 200.
При установленном тогда интервале **2,5 секунды** начальная загрузка в Chromium заняла 33,1 секунды, обновление
после отключения пятикомнатных квартир — 34,6 секунды. Все 28 CRM-запросов и оба
ответа `/api/report` вернули 200, REST-ошибок и ошибок JavaScript не было.
Минимальный интервал начала запросов составил 2500,47 мс, включая границу между
загрузками. Само отключение пятикомнатных квартир не создало новых запросов,
после обновления эта комната осталась выключенной.
Связь ранее замеченной ошибки повторного обновления с фильтром комнат или лимитом
CRM этими замерами не установлена: фильтры применяются локально, их значения
не отправляются в CRM.

Приведённые выше длительности с интервалом 2,5 секунды относятся к прежней реализации.

## Живая проверка скорости отчёта

После настройки вебхука выполните отдельную команду:

```sh
npm run test:crm-performance
```

Она не входит в `npm test` и обращается к рабочей CRM. Команда использует ту же
настройку и `loadReport`, что сервер, и выполняет пять последовательных полных
загрузок, начиная с холодного запуска. Время включает метаданные, все страницы,
сетевое ожидание, паузы очереди и агрегацию. Прогрева, кеша, повторов и исключения
выбросов нет. Код 0 означает пять успешных загрузок и неокруглённое среднее
не более 4000 мс; иначе код 1. Первый неуспешный ответ прекращает проверку.
В вывод попадают только номер замера, длительность, локальный статус,
количество HTTP-запросов и сводка; длительности округляются только для вывода.
Записи CRM и URL вебхука не печатаются.

28 октября 2026 года после введения пакетного чтения и интервала 200 мс проверка
завершилась `PASS`: пять полных загрузок вернули 200, каждая использовала
5 HTTP-запросов. Длительности — **1893, 1263, 1199, 1327, 2342 мс**;
среднее в округлённом выводе — **1605 мс**, минимум — 1199 мс, максимум — 2342 мс.
Серия до пакетного чтения использовала по 14 запросов и заняла
4301, 4797, 6938, 6941, 7007 мс, со средним 5997 мс.
Реальные записи не сохранялись. Это измерение конкретного портала в момент
проверки, а не гарантия длительности при любой сети, объёме данных или нагрузке.
