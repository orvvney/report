# Тестирование

## Стек и установка

Jest запускает оба набора тестов: `unit` и `e2e`. В e2e используется библиотека
Playwright и настоящий Chromium; отдельного раннера Playwright Test нет.
Все команды выполняются из корня проекта. Нужны Node.js 22.12.0+ и npm.
Версии npm-зависимостей закреплены в `package.json` и `package-lock.json`.

Первый запуск после клонирования:

```sh
npm ci
npm run test:install
npm test
```

`test:install` скачивает Chromium, совместимый с установленным Playwright.
Повторяйте эту команду после обновления Playwright. Браузер хранится в системном
кэше Playwright вне репозитория. Для Linux CI с недостающими системными библиотеками
используйте `npx playwright install --with-deps chromium`.

## Команды

| Команда | Назначение |
| --- | --- |
| `npm test` | Все unit и e2e тесты, последовательно |
| `npm run test:unit` | Все unit тесты, браузер не нужен |
| `npm run test:unit:watch` | Unit тесты с перезапуском при изменениях |
| `npm run test:e2e` | Production-сборка и все e2e с автоматическим сервером и браузером |
| `npm run build` | Отдельная production-сборка Vue/Tailwind в `dist/` |
| `npm run dev` | Сборка при изменениях в `dist-dev/`, локальный сервер и автообновление страницы |
| `npm run test:ci` | Оба набора в режиме Jest CI |
| `npm run test:crm-performance` | Отдельная живая проверка: пять полных загрузок CRM, среднее не более 4000 мс |
| `E2E_HEADED=1 npm run test:e2e` | E2e с видимым Chromium, синтаксис macOS/Linux |

Один файл или сценарий во время разработки:

```sh
npm run test:unit -- --runTestsByPath tests/unit/bitrix24.test.js
npm run test:e2e -- --runTestsByPath tests/e2e/home.test.js
npm run test:e2e -- -t 'loads the built report'
```

**После каждого изменения функционала запускайте `npm test`.** Это включает полный
набор e2e. Проверки только одного нового файла недостаточно для сдачи задачи.
Для отдельного повторного прогона всех браузерных сценариев есть `npm run test:e2e`.
API-тесты в наборе `unit` также открывают локальный HTTP-порт; им нужны
разрешения на `listen`. Успешный процесс возвращает код 0; падение или отсутствие выбранных тестов — ненулевой код.

## Организация

```text
jest.config.cjs                    # Два проекта Jest: unit и e2e
tests/
  unit/**/*.test.js                # Изолированные проверки логики
  e2e/**/*.test.js                 # Пользовательские сценарии в браузере
  support/global-setup.cjs         # Production-сборка и запуск createServer() перед e2e
  support/global-teardown.cjs      # Остановка сервера после e2e
  support/browser.cjs              # Браузер и изоляция тестов
  support/dev-server.cjs           # Изолированный dev-сервер с искусственной CRM
```

`home.test.js` проверяет HTTP и собранное приложение, `/index.html` с query,
UTF-8, `HEAD` без тела, неизвестные пути/методы и запрет чтения секретов,
Git, исходников и конфигурации. `bitrix24.test.js` проверяет реальную CLI
и модули интеграции на искусственных ответах API.

Тесты написаны на JavaScript с CommonJS (`require`). Unit работают в Node.js,
DOM-окружения для них нет. Браузер проверяет настоящую Vue-сборку, а не DOM-мок.
Внешний транспорт заменяет [`crm-fixture.cjs`](../tests/support/crm-fixture.cjs):
он применяет фильтры и `select`, разбивает данные на страницы, позволяет менять
снимок, задерживать ответ и воспроизводить отказ последней страницы.
Рабочий `.env`, внешняя сеть и реальные записи CRM в автотестах не используются.
В обычных API/CLI/e2e-фикстурах `scheduleRequest` явно заменён немедленным
выполнением, чтобы не ждать реальные 200 мс на каждом вызове. Саму очередь
проверяет [`request-scheduler.test.js`](../tests/unit/request-scheduler.test.js)
с виртуальными таймерами Jest: 14 запросов и следующий запуск, общая очередь
разных клиентов и вебхуков одного портала, отсутствие пересечения медленных
запросов, освобождение очереди после ошибки/таймаута и отсчёт таймаута только
после выхода из очереди. Дополнительный сценарий запускает настоящий `loadReport`
с планировщиком и 503 искусственными сделками: 5 HTTP-ответов с задержкой 500 мс
каждый и дополнительными 50 мс на каждую команду пакета дают полный отчёт
за 3000 мс виртуального времени, 503 сделки и сумму 5030.
Это проверка алгоритма с заданными задержками, а не гарантия скорости живой CRM.

  затем обновление. Дополнительно проверяются точные тексты X/Y, отсутствие строки
  периода, прямоугольная кнопка `Թարմացնել հաշվետվությունը` с тем же размером
  текста, что у подписи Y, её расположение справа на 1440 px и перенос ниже Y
  на 375 px, центрирование `Ցուցադրություն`,
  нижняя компоновка и одновременная видимость X/кнопки проблем. Проверки реальной
  SVG-геометрии выявляют пересечения и обрезку длинных сумм и названий категорий.
  В обоих режимах и размерах окна проверяются ширина столбцов 56 CSS px, цвет
  столбцов/полных сумм `#6685EB`, подписи `N գործարք`, пунктир сетки выше нуля
  и концы вертикальной оси от нуля до U. Нижняя линия X проверяется как сплошная,
  горизонтальная и доходящая до общего правого края сетки.
  Время и общий счётчик лежат на одной строке,
  разделены `·`; названия осей используют `·` и прописные X/Y.
  Счётчик и шкала меняются от режима/фильтров без запроса; время меняется только
  после успешной загрузки. Часы браузера фиксируются отдельно от времени fixture
  сервера. Загрузка/ошибка скрывают нижнюю информацию, пустой успех показывает
  новое время, N=0 и нулевые подписи.

## Проверки Битрикс24

[`bitrix24.test.js`](../tests/unit/bitrix24.test.js) покрывает приоритет окружения,
неверную конфигурацию, запуск исполняемого CLI, точный поиск и неоднозначность
метаданных, основную воронку с ID 0, 51 сделку на двух страницах, максимум пять
примеров, пустые значения и исходные типы данных. Сценарии ошибок включают HTTP,
REST, неверный JSON, таймаут запроса и тела ответа, отказ следующей страницы,
некорректную пагинацию, нарушение фильтра/порядка и сокрытие секрета в диагностике.
Отдельная регрессия подтверждает, что CLI сохраняет все типы недвижимости
и не требует метаданных поля типа.

[`batch.test.js`](../tests/unit/batch.test.js) проверяет наборы из 0, 50, 51, 503
и 2553 сделок, совпадение отчёта с последовательной загрузкой, предел 50 команд
на пакет и переход к следующему пакету. Проверяются ошибки и пропущенные
результаты команд, неполные страницы, изменение `total`, неверный `next`,
фильтр и порядок ID, кодирование вложенных параметров и список разрешённых
методов. Ошибочные пакеты не превращаются в частичный успешный отчёт.

[`report-performance.test.js`](../tests/unit/report-performance.test.js)
проверяет алгоритм отдельной живой CLI на искусственном загрузчике: учёт всех
пяти замеров, неокруглённую границу 4000 мс (4000,1 мс уже не проходит),
досрочное завершение при отказе и отсутствие содержимого отчёта в выводе.
Сам `npm run test:crm-performance` не входит в `npm test` и требует реальной
настройки CRM. Его правила и фактические замеры — в
[инструкции интеграции](bitrix24.md#живая-проверка-скорости-отчёта).

Регрессионный сценарий проверяет одновременное получение стандартных и
пользовательских полей в режиме `useOriginalUfNames: 'N'`. Искусственная фикстура
применяет `select` и воспроизводит наблюдавшееся на портале отсутствие стандартных
полей при `Y`. Тест сначала выявил сбой, затем прошёл после исправления;
реальные записи CRM в фикстуру не переносились.

Живая проверка `npm run bitrix:check` 21 октября 2026 года завершилась кодом 0;
количество и примеры независимо сверены с CRM. Результат, границы сверки и причина
выбора режима имён полей описаны в [инструкции интеграции](bitrix24.md).
Проверка пустой настройки отдельно подтвердила код 1 и инструкцию заполнить `.env`.

## Принцип создания unit тестов

- Добавляйте `tests/unit/<feature>.test.js`, импортируйте реальную функцию приложения.
- Проверяйте наблюдаемый результат: обычный случай, важные границы, ошибки входных данных.
- Структура: подготовка данных → действие → проверка результата.
- Изолируйте внешние сервисы, часы и случайность, когда от них зависит результат.
  Не подменяйте саму проверяемую функцию и не копируйте её реализацию в тест.
- Тесты не должны зависеть от порядка запуска, сети или данных другого теста.

Примеры проверок конфигурации, API и CLI находятся в
[`tests/unit/bitrix24.test.js`](../tests/unit/bitrix24.test.js).

## Принцип создания e2e тестов

Добавляйте `tests/e2e/<feature>.test.js`. Используйте обычные Jest `describe`, `test`,
`expect`; глобальный `page` предоставляет `tests/support/browser.cjs`.
Не импортируйте `test` из `@playwright/test`.

Setup сначала запускает Vite с `NODE_ENV=production`, затем импортирует
`createServer()` из [`server.js`](../server.js) и запускает его с искусственным
CRM-транспортом на `127.0.0.1` и свободном порту. Отдельные `npm run build`
и `npm start` перед e2e не нужны. `page.goto('/')` использует этот адрес.
Это тот же сервер и API, которые запускает `npm start`; корень проекта не раздаётся.
Сценарии отчёта создают отдельный сервер со своей fixture для изоляции состояния.

В каждом файле запускается Chromium, а **перед каждым тестом создаётся новый
контекст и страница**. Cookies и localStorage не переносятся между тестами.
После теста контекст закрывается; после файла — браузер; после набора — сервер.
Не используйте `test.concurrent` с общим `page`. Состояние fixture сервера
готовьте отдельно для каждого сценария.

Текущий рабочий пример:

```js
test('страница показывает заголовок отчёта', async () => {
  const response = await page.goto('/');

  expect(response.status()).toBe(200);
  await page.getByRole('heading', { name: 'Կնքված բնակարանների հաշվետվություն', level: 1, exact: true })
    .waitFor({ state: 'visible' });
  expect(await page.locator('html').getAttribute('lang')).toBe('hy');
});
```

- Формулируйте тест как пользовательский сценарий: открыть страницу, выполнить
  действие, увидеть результат. Для нового функционала покрывайте основной путь
  и значимый отказ или граничный случай.
- Предпочитайте `getByRole`, `getByLabel`, видимый текст; `getByTestId` используйте,
  когда семантического локатора недостаточно. Избегайте CSS-классов оформления и XPath.
- Дожидайтесь видимого результата через локаторы и `waitFor`, ответа через
  `waitForResponse` или навигации через `waitForURL`. Ожидание ответа регистрируйте
  до действия. Не используйте фиксированные `sleep`/`waitForTimeout`.
- Здесь `expect` принадлежит Jest: проверки не повторяются автоматически,
  матчеров `toBeVisible` и `toHaveText` из Playwright Test нет. Сначала дождитесь
  нужного состояния, затем проверьте значение обычным Jest `expect`.
- Не заменяйте страницу через `page.setContent` и не мокайте собственную
  функциональность в основном e2e сценарии. Внешние интеграции можно подменять
  явно, описав границы такого сценария.
- Каждый тест сам готовит необходимые данные. Не завязывайтесь на внешние сайты,
  личные аккаунты или секреты; не полагайтесь на успешность предыдущего теста.
- Для e2e лимит теста — 30 секунд, действий — 10 секунд, навигации — 15 секунд.
  Увеличивайте лимиты только при объяснимой потребности, не для маскировки ошибок.

## Работа вместе с агентами

1. Перед реализацией прочитайте этот документ и связанные тесты. Сопоставьте
   критерии приёмки с unit-проверками и браузерными сценариями.
2. Реализуйте функционал и тесты в одной задаче. Если работа уже распределена между
   агентами, назначьте владельцев файлов и согласуйте локаторы и тестовые данные;
   общую конфигурацию и fixtures меняйте согласованно.
3. Во время разработки запускайте затронутый файл. При исправлении бага добавьте
   сценарий, воспроизводящий проблему; убедитесь, что он различает ошибочное и
   исправленное поведение. Не ослабляйте проверки ради зелёного результата.
4. После интеграции всех изменений выполните `npm test` без фильтров. Не оставляйте
   `.only`, необоснованные `.skip` и незавершённые проверки.
5. В отчёте укажите выполненные команды, результат, количество тестов и ограничения.
   Если окружение заблокировало запуск, сообщите об этом явно, не заявляйте об успехе.
6. После успешных проверок запустите `docs-maintainer` по
   [правилам документации](documentation.md) и дождитесь результата до сдачи.

## Диагностика и CI

Если Chromium отсутствует, выполните `npm run test:install`. При запрете запуска
процесса браузера или локального HTTP-сервера нужны разрешения окружения.
Не обходите проблему заменой e2e на DOM-моки.

Для поиска зависших ресурсов:

```sh
npm test -- --detectOpenHandles
```

Для временного снимка в процессе отладки: создайте каталог `test-results/` и вызовите
`await page.screenshot({ path: 'test-results/debug.png', fullPage: true })`.
Сценарий шапки сохраняет `test-results/header-1440.png`.
Сценарий адаптивности отчёта сохраняет `report-wide.png`, `report-narrow.png`
и `report-modal.png` в `test-results/`. Сценарий панели также сохраняет
`filters-error-1440.png`, `filters-error-375.png`, `filters-date-control-1440.png`
и `filters-date-control-375.png`. Последние два снимка не захватывают нативное
всплывающее окно календаря. Сообщение о недоступности фильтров сохраняется
при загрузке в `filters-loading-{1440,375}.png`, при ошибке —
в `filters-unavailable-{1440,375}.png`. Сценарии дизайна сохраняют
`chart-{rooms,months}-{1440,375}.png` и варианты с суффиксом `-end` после
прокрутки к последней категории. Геометрия фильтров сохраняет
`filters-layout-{1440,1024,375,320}.png` и варианты
`filters-layout-{1440,1024,375,320}-{4,6,12}.png`. Варианты фильтров с суффиксом
`-end` больше не создаются: такие файлы в `test-results/` относятся к прежней
компоновке с прокруткой. Подсказки сохраняются в
`filters-hints-{1440,375}-{amount,area,date}-{empty,filled}.png`;
частичная дата — в `filters-hints-{1440,375}-date-partial.png`.
Поля с единицами сохраняются в
`filters-units-{1440,375}-{amount,area}-{empty,filled}.png`.
Общий сбор скриншотов при падении и трассировок
не настроен.
`node_modules/`, `dist/`, `dist-dev/`, `coverage/` и `test-results/` исключены из Git.

CI workflow пока не добавлен. Последовательность для будущего Linux job:

```sh
npm ci
npx playwright install --with-deps chromium
npm run test:ci
```

При установке зависимостей 22 октября 2026 года npm сообщил о 19 предупреждениях
уровня moderate, без high/critical. При предыдущей диагностике 19 октября
цепочка в dev-зависимостях Jest вела к `sprintf-js` через `argparse` и `js-yaml`;
предложенный тогда `audit fix --force` откатывал Jest до 25.0.0. Принудительное
обновление не применялось. При обновлении
зависимостей повторяйте аудит и полный прогон тестов.

Справка: [конфигурация Jest](https://jestjs.io/docs/configuration),
[CLI Jest](https://jestjs.io/docs/cli),
