# Тестирование

## Стек и установка

Jest запускает оба набора тестов: `unit` и `e2e`. В e2e используется библиотека
Playwright и настоящий Chromium; отдельного раннера Playwright Test нет.
Все команды выполняются из корня проекта. Нужны Node.js 22+ и npm.
Версии npm-зависимостей закреплены в `package.json` и `package-lock.json`.

Первый запуск после клонирования:

```sh
npm ci
npm run test:install
npm test
```

`test:install` скачивает Chromium, совместимый с установленным Playwright.
Повторяйте эту команду после обновления Playwright. Браузер хранится в системном
кэше Playwright вне репозитория. Для Linux CI с недостающими системными библиотеками
используйте `npx playwright install --with-deps chromium`.

## Команды

| Команда | Назначение |
| --- | --- |
| `npm test` | Все unit и e2e тесты, последовательно |
| `npm run test:unit` | Все unit тесты, браузер не нужен |
| `npm run test:unit:watch` | Unit тесты с перезапуском при изменениях |
| `npm run test:e2e` | Все e2e тесты с автоматическим сервером и браузером |
| `npm run test:ci` | Оба набора в режиме Jest CI |
| `E2E_HEADED=1 npm run test:e2e` | E2e с видимым Chromium, синтаксис macOS/Linux |

Один файл или сценарий во время разработки:

```sh
npm run test:unit -- --runTestsByPath tests/unit/bitrix24.test.js
npm run test:e2e -- --runTestsByPath tests/e2e/home.test.js
npm run test:e2e -- -t 'loads the starter page'
```

**После каждого изменения функционала запускайте `npm test`.** Это включает полный
набор e2e. Проверки только одного нового файла недостаточно для сдачи задачи.
Для отдельного повторного прогона всех браузерных сценариев есть `npm run test:e2e`.
Успешный процесс возвращает код 0; падение или отсутствие выбранных тестов — ненулевой код.

## Организация

```text
jest.config.cjs                    # Два проекта Jest: unit и e2e
tests/
  unit/**/*.test.js                # Изолированные проверки логики
  e2e/**/*.test.js                 # Пользовательские сценарии в браузере
  support/global-setup.cjs         # Запуск createServer() из server.js перед e2e
  support/global-teardown.cjs      # Остановка сервера после e2e
  support/browser.cjs              # Браузер и изоляция тестов
```

Сейчас исходная страница содержит только `test` и `hello world`.
`home.test.js` проверяет HTTP 200, видимое содержимое, выдачу `/index.html` с
query-параметрами, UTF-8, `HEAD` без тела с верной длиной содержимого,
404 для неизвестных путей и `POST`, запрет выдачи `.env`, его вариантов,
файлов Git, исходников и `package.json`. `bitrix24.test.js` проверяет реальную CLI и модули
интеграции на искусственных ответах API. Внешний транспорт подменяется; рабочий
`.env`, сеть и реальные данные CRM в автотестах не используются. Учебный
unit-пример заменён тестами интеграции.

Тесты написаны на JavaScript с CommonJS (`require`). TypeScript, JSX, трансформация
фреймворков и DOM-окружение для unit пока не настроены. Unit выполняются в Node.js;
браузерное поведение проверяется в e2e.

## Проверки Битрикс24

[`bitrix24.test.js`](../tests/unit/bitrix24.test.js) покрывает приоритет окружения,
неверную конфигурацию, запуск исполняемого CLI, точный поиск и неоднозначность
метаданных, основную воронку с ID 0, 51 сделку на двух страницах, максимум пять
примеров, пустые значения и исходные типы данных. Сценарии ошибок включают HTTP,
REST, неверный JSON, таймаут запроса и тела ответа, отказ следующей страницы,
некорректную пагинацию, нарушение фильтра/порядка и сокрытие секрета в диагностике.

Регрессионный сценарий проверяет одновременное получение стандартных и
пользовательских полей в режиме `useOriginalUfNames: 'N'`. Искусственная фикстура
применяет `select` и воспроизводит наблюдавшееся на портале отсутствие стандартных
полей при `Y`. Тест сначала выявил сбой, затем прошёл после исправления;
реальные записи CRM в фикстуру не переносились.

Живая проверка `npm run bitrix:check` 21 октября 2026 года завершилась кодом 0;
количество и примеры независимо сверены с CRM. Результат, границы сверки и причина
выбора режима имён полей описаны в [инструкции интеграции](bitrix24.md).
Проверка пустой настройки отдельно подтвердила код 1 и инструкцию заполнить `.env`.

## Принцип создания unit тестов

- Добавляйте `tests/unit/<feature>.test.js`, импортируйте реальную функцию приложения.
- Проверяйте наблюдаемый результат: обычный случай, важные границы, ошибки входных данных.
- Структура: подготовка данных → действие → проверка результата.
- Изолируйте внешние сервисы, часы и случайность, когда от них зависит результат.
  Не подменяйте саму проверяемую функцию и не копируйте её реализацию в тест.
- Тесты не должны зависеть от порядка запуска, сети или данных другого теста.

Примеры проверок конфигурации, API и CLI находятся в
[`tests/unit/bitrix24.test.js`](../tests/unit/bitrix24.test.js).

## Принцип создания e2e тестов

Добавляйте `tests/e2e/<feature>.test.js`. Используйте обычные Jest `describe`, `test`,
`expect`; глобальный `page` предоставляет `tests/support/browser.cjs`.
Не импортируйте `test` из `@playwright/test`.

Setup импортирует `createServer()` из корневого [`server.js`](../server.js),
запускает его на `127.0.0.1` и свободном порту; отдельный `npm start` перед e2e не нужен.
Он отдаёт содержимое `index.html` только для `GET`/`HEAD` по `/` и `/index.html`;
остальные пути и методы возвращают 404. Корень проекта не раздаётся, чтобы
локальный `.env` не попал в HTTP-ответ. `page.goto('/')` использует этот адрес.
Это тот же сервер, который запускает `npm start`, без дублирования обработчика
в тестовой инфраструктуре. При добавлении сборки или API поддерживайте setup/teardown
в соответствии с запуском приложения; сейчас сервер не выполняет сборку или API.

В каждом файле запускается Chromium, а **перед каждым тестом создаётся новый
контекст и страница**. Cookies и localStorage не переносятся между тестами.
После теста контекст закрывается; после файла — браузер; после набора — сервер.
Не используйте `test.concurrent` с общим `page`. При появлении backend изоляцию
данных сервера нужно будет организовать отдельно.

Текущий рабочий пример:

```js
test('страница показывает стартовый текст', async () => {
  const response = await page.goto('/');

  expect(response.status()).toBe(200);
  await page.getByText('hello world', { exact: false }).waitFor({ state: 'visible' });
  expect(await page.locator('body').innerText()).toMatch(/hello world/);
});
```

- Формулируйте тест как пользовательский сценарий: открыть страницу, выполнить
  действие, увидеть результат. Для нового функционала покрывайте основной путь
  и значимый отказ или граничный случай.
- Предпочитайте `getByRole`, `getByLabel`, видимый текст; `getByTestId` используйте,
  когда семантического локатора недостаточно. Избегайте CSS-классов оформления и XPath.
- Дожидайтесь видимого результата через локаторы и `waitFor`, ответа через
  `waitForResponse` или навигации через `waitForURL`. Ожидание ответа регистрируйте
  до действия. Не используйте фиксированные `sleep`/`waitForTimeout`.
- Здесь `expect` принадлежит Jest: проверки не повторяются автоматически,
  матчеров `toBeVisible` и `toHaveText` из Playwright Test нет. Сначала дождитесь
  нужного состояния, затем проверьте значение обычным Jest `expect`.
- Не заменяйте страницу через `page.setContent` и не мокайте собственную
  функциональность в основном e2e сценарии. Внешние интеграции можно подменять
  явно, описав границы такого сценария.
- Каждый тест сам готовит необходимые данные. Не завязывайтесь на внешние сайты,
  личные аккаунты или секреты; не полагайтесь на успешность предыдущего теста.
- Для e2e лимит теста — 30 секунд, действий — 10 секунд, навигации — 15 секунд.
  Увеличивайте лимиты только при объяснимой потребности, не для маскировки ошибок.

## Работа вместе с агентами

1. Перед реализацией прочитайте этот документ и связанные тесты. Сопоставьте
   критерии приёмки с unit-проверками и браузерными сценариями.
2. Реализуйте функционал и тесты в одной задаче. Если работа уже распределена между
   агентами, назначьте владельцев файлов и согласуйте локаторы и тестовые данные;
   общую конфигурацию и fixtures меняйте согласованно.
3. Во время разработки запускайте затронутый файл. При исправлении бага добавьте
   сценарий, воспроизводящий проблему; убедитесь, что он различает ошибочное и
   исправленное поведение. Не ослабляйте проверки ради зелёного результата.
4. После интеграции всех изменений выполните `npm test` без фильтров. Не оставляйте
   `.only`, необоснованные `.skip` и незавершённые проверки.
5. В отчёте укажите выполненные команды, результат, количество тестов и ограничения.
   Если окружение заблокировало запуск, сообщите об этом явно, не заявляйте об успехе.
6. После успешных проверок запустите `docs-maintainer` по
   [правилам документации](documentation.md) и дождитесь результата до сдачи.

## Диагностика и CI

Если Chromium отсутствует, выполните `npm run test:install`. При запрете запуска
процесса браузера или локального HTTP-сервера нужны разрешения окружения.
Не обходите проблему заменой e2e на DOM-моки.

Для поиска зависших ресурсов:

```sh
npm test -- --detectOpenHandles
```

Для временного снимка в процессе отладки: создайте каталог `test-results/` и вызовите
`await page.screenshot({ path: 'test-results/debug.png', fullPage: true })`.
Автоматический сбор скриншотов и трассировок не настроен.
`node_modules/`, `coverage/` и `test-results/` исключены из Git.

CI workflow пока не добавлен. Последовательность для будущего Linux job:

```sh
npm ci
npx playwright install --with-deps chromium
npm run test:ci
```

При установке 19 октября 2026 года `npm audit` сообщил о 19 предупреждениях
уровня moderate в dev-зависимостях Jest: цепочка ведёт к `sprintf-js` через
`argparse` и `js-yaml`. Предупреждений high/critical не было. Предложенный npm
`audit fix --force` откатывает Jest до 25.0.0 и не применялся. При обновлении
зависимостей повторяйте аудит и полный прогон тестов.

Справка: [конфигурация Jest](https://jestjs.io/docs/configuration),
[CLI Jest](https://jestjs.io/docs/cli),
[браузеры Playwright](https://playwright.dev/docs/browsers).
