# Подключение Битрикс24 и проверка получения успешных сделок через терминал

Статус: готова к реализации

## Контекст и цель

Будущий сайт предназначен для отчёта руководителям об успешных сделках компании.
Текущий этап ограничен подключением к REST API облачного Битрикс24 через входящий
вебхук и проверкой получения данных локальной командой в терминале.

В проекте сейчас есть стартовый `index.html`, Node.js 22+, npm и тестовая
инфраструктура Jest с браузерными e2e на Playwright. При исследовании прочитаны
`package.json`, `jest.config.cjs`, `tests/unit/example.test.js`,
`tests/e2e/home.test.js`, `tests/support/global-setup.cjs`,
`tests/support/browser.cjs` и [инструкция по тестированию](../docs/testing.md).
Интеграции, backend и прикладной логики пока нет. В `.gitignore` пока отсутствует
правило исключения `.env`.

## Объём задачи

Добавить локальную настройку вебхука, модуль чтения API и команду
`npm run bitrix:check`. Команда должна найти нужные настройки CRM, получить все
доступные подходящие сделки и показать количество и несколько примеров значений.

Сайт, страницы проверки, таблицы отчёта, графики, авторизация, размещение,
постоянное хранение сделок, расписание обновлений и изменения данных CRM
в этот этап не входят. Существующая стартовая страница сохраняется.

## Требования

### 1. Настройка и защита вебхука

- Создать в корне `.env.example` с пустой переменной `BITRIX24_WEBHOOK_URL=`
  и кратким пояснением: требуется базовый URL входящего вебхука без имени
  REST-метода. Реальных значений в примере быть не должно.
- Создать локальный `.env` с той же пустой переменной, если файла ещё нет.
  Существующий `.env` не перезаписывать и не выводить его содержимое.
- Исключить `.env` и локальные варианты `.env.*` из Git, оставив
  `.env.example` доступным для версионирования. Проверить исключение через
  `git check-ignore`, а также отсутствие `.env` среди отслеживаемых файлов.
- Пользователь самостоятельно вставляет вебхук в `.env`. Не просить секрет
  в чате и не записывать его в исходники, документацию, тестовые данные или
  npm-команду. Переменная окружения процесса имеет приоритет над `.env`.
- Команда выполняет обращения из Node.js; URL вебхука не попадает в браузер.
  Не выводить полный URL, токен, необработанные сетевые исключения или ответы
  об ошибках, способные содержать секрет, в stdout/stderr.
- При отсутствии или некорректном значении настройки завершаться с ненулевым
  кодом и понятной инструкцией заполнить `.env`, без сетевых обращений.
  Для реального вебхука использовать HTTPS.

### 2. Поиск воронки, стадии и полей

Использовать только методы чтения:

1. Получить воронки сделок и найти точное название `Վաճառք`.
2. Получить стадии именно этой воронки и найти точное название `Կնքված`.
3. Получить метаданные полей сделки и определить коды трёх пользовательских
   полей по указанным ниже названиям. Показать найденные коды и типы в диагностике.
4. Использовать найденные идентификаторы в запросах сделок, не придумывать
   значения и не привязывать реализацию к ID тестового портала.

| Название в CRM | Источник | Подпись в диагностическом примере |
| --- | --- | --- |
| `Սենյակների քանակ` | Пользовательское поле | `Սենյակների քանակ` |
| Сумма | Системное поле суммы сделки | `Ընդհանուր արժեք` |
| `Մակերես (մ²)` | Пользовательское поле | `Մակերես (մ²)` |
| `Կնքման ամսաթիվ` | Пользовательское поле | `Կնքման ամսաթիվ` |

Если воронка, стадия или поле не найдены либо название соответствует нескольким
кандидатам, прекращать проверку с ненулевым кодом и диагностикой проблемного
названия и найденных кандидатов. Не выбирать первый результат произвольно.
Не заменять пользовательскую дату системной датой закрытия.
Критерий выборки — именно заданная воронка и стадия; дополнительный фильтр
по общей семантике успешности не вводить.

### 3. Загрузка и диагностический результат

- Получить все сделки, доступные владельцу вебхука, из найденной воронки
  на найденной стадии, без ограничения по дате.
- Обработать пагинацию до конца. Результат первой страницы не считать полным.
  Использовать стабильную сортировку по ID по возрастанию.
- Запрашивать три найденных пользовательских поля и системную сумму;
  дополнительно допустимы ID сделки, идентификаторы воронки и стадии для проверки
  отбора и код валюты для понимания суммы. Контакты и прочие поля не запрашивать.
- Вывести найденные воронку и стадию с идентификаторами, соответствие названий
  пользовательских полей кодам и типам, количество загруженных сделок и до пяти
  первых сделок с ID и четырьмя требуемыми полями. Сумму сопровождать кодом валюты.
- На этом этапе показывать значения API без расчётов, округления, конвертации
  валют и преобразования часового пояса. Если поле является списком или массивом,
  сохранить исходное значение, не придумывать его числовую интерпретацию.
- Пустые строки, `null` и отсутствующие значения явно обозначать как незаполненные.
  Числовой ноль не считать отсутствием значения. Сделки с пустыми полями
  не исключать из количества.
- Если после успешного поиска метаданных сделок нет, вывести «Сделок не найдено»,
  количество 0 и завершиться с кодом 0.
- При полном успешном чтении завершиться с кодом 0. При отказе доступа, ошибке
  REST даже с HTTP 200, сетевом сбое, таймауте или некорректном ответе —
  с ненулевым кодом и безопасным сообщением о шаге и причине.
  Предусмотреть конечный таймаут запроса; бесконечные ожидания и повторы исключить.
- Если последующая страница недоступна, не выдавать уже загруженную часть за
  полный успешный результат.
- Не сохранять выгрузки и реальные ответы API в файлы проекта. Диагностические
  сообщения — на русском, исходные армянские названия сохраняются.

## Технический подход и подтверждённые контракты

Добавить небольшой модуль на JavaScript для Node.js и CLI-обёртку, совместимые
с существующими CommonJS-тестами. Использовать встроенные возможности Node.js
для HTTP и загрузки окружения; отдельный сервер, UI-фреймворк и база данных
не требуются. Отделить вызов API, поиск метаданных и получение сделок от вывода,
чтобы проверки не зависели от рабочего портала.

Рекомендуемые точки добавления: `src/bitrix24/` для интеграции,
`scripts/bitrix-check.cjs` для команды; имена внутренних модулей исполнитель
может выбрать без изменения поведения.

Контракты проверены по официальной документации 20 октября 2026 года:

- Воронки: `crm.category.list`, `entityTypeId: 2` для сделок.
  [Описание метода](https://apidocs.bitrix24.com/api-reference/crm/universal/category/crm-category-list.html).
- Стадии: `crm.status.list`; справочник `DEAL_STAGE` для основной воронки
  и `DEAL_STAGE_<ID>` для остальных. Для фильтра сделок нужен `STATUS_ID`,
  а не числовой ID записи справочника.
  [Сделки и воронки](https://apidocs.bitrix24.com/api-reference/crm/deals/),
  [метод справочника](https://apidocs.bitrix24.com/api-reference/crm/status/crm-status-list.html).
- Поля: `crm.item.fields`, `entityTypeId: 2`. Системная сумма — `opportunity`,
  валюта — `currencyId`; названия и типы пользовательских полей берутся из
  метаданных. В метаданных и чтении использовать одинаковый режим
  `useOriginalUfNames: 'Y'`.
  [Описание полей](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-fields.html).
- Сделки: `crm.item.list`, `entityTypeId: 2`, фильтры `categoryId` и `stageId`,
  явный `select`, порядок `id: 'ASC'`. Следующий запрос использует значение
  `next` ответа как `start`; размер страницы — 50. Метод возвращает только
  доступные пользователю записи.
  [Описание списка](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html).

Реальные идентификаторы, типы полей, количество сделок и права пользователя
вебхука ещё не проверялись. Они определяются при исполнении команды.

## Критерии приёмки

- **К1.** Пользователь может вставить URL в локальный `.env` и запустить
  `npm run bitrix:check`; секрет исключён из Git и вывода команды.
- **К2.** Команда однозначно находит заданные воронку, стадию и пользовательские
  поля и выводит их идентификаторы; отсутствие или неоднозначность дают ошибку.
- **К3.** Команда получает все страницы только подходящих сделок и выводит
  полное количество и не более пяти примеров с нужными подписями и значениями.
- **К4.** Пустая выборка и незаполненные значения обрабатываются явно; нули
  сохраняются; суммы и даты не преобразуются.
- **К5.** Ошибки конфигурации, доступа, сети и REST приводят к ненулевому коду
  без утечки секрета; неполная загрузка не считается успешной.
- **К6.** Выполнена живая проверка после настройки вебхука, результат сверён
  с доступными в CRM данными. При отсутствии доступа этот критерий остаётся
  непроверенным и успешная проверка интеграции не заявляется.
- **К7.** Все автоматические тесты проекта, включая существующие браузерные e2e,
  проходят; документация настройки и проверки актуализирована через
  `docs-maintainer`, ссылки проверены.

## Сценарии тестирования

Тестовые ID, URL и записи должны быть искусственными. Автотесты не используют
рабочий `.env`, внешний интернет и реальные данные CRM.

| Критерий | Исходное состояние и действие | Ожидаемый результат | Уровень |
| --- | --- | --- | --- |
| К1, К5 | Нет `.env`/переменной, пустое или неверное значение; запустить CLI | Ненулевой код, инструкция настройки, сетевых запросов нет | Автотест CLI |
| К1 | Задать разные искусственные значения в окружении и временном `.env`; выполнить загрузку конфигурации | Значение окружения имеет приоритет; исходный файл не изменён | Unit |
| К1 | Проверить правила Git для `.env`, `.env.local`, `.env.example` и отслеживаемые файлы | Секретные файлы игнорируются и не отслеживаются, пример доступен для Git | Ручная, команды Git |
| К2 | Метаданные содержат целевые названия, посторонние воронки и одноимённую стадию другой воронки | Выбрана стадия только нужной воронки; получены реальные коды трёх полей | Unit/API с фиктивными ответами |
| К2, К5 | По очереди убрать или продублировать целевую воронку, стадию и поле | Явная ошибка соответствующего поиска, произвольного выбора и чтения сделок нет | Unit |
| К3 | Фиктивный API содержит 51 подходящую сделку и посторонние записи; вызвать полную загрузку | Запросы содержат нужные фильтры и select, обработаны 2 страницы, количество 51, примеров 5, последняя запись не потеряна | API и CLI с подменой внешнего транспорта |
| К4 | Метаданные корректны, список сделок пуст | Код 0, количество 0 и сообщение об отсутствии сделок | Автотест CLI |
| К3, К4 | Вернуть 2 сделки с нулём, дробной суммой, датой, `null`, пустой строкой и массивом в пользовательском поле | Примеров 2; исходные значения и подписи сохранены, пустые значения обозначены, ноль не пропал | Unit/CLI |
| К1, К5 | Имитировать HTTP-отказ, REST error с HTTP 200, неверный JSON, таймаут и ошибку второй страницы; в исходные ошибки включить тестовый секрет | Ненулевой код, безопасная диагностика, нет секрета и сообщения о полном успехе | API/CLI |
| К6 | Пользователь настроил вебхук с CRM-доступом и чтением нужных сделок; выполнить команду | Найдены метаданные, загружены доступные сделки, количество и примеры сверены с CRM; при нуле зафиксирована граница проверки значений | Ручная интеграционная |
| К7 | Запустить `npm test` после реализации | Все unit и e2e проходят, исходная страница продолжает открываться | Полный автоматический прогон |
| К7 | После проверок запустить документатора и проверить его результат | В `docs/` есть актуальные инструкции настройки, запуска и диагностики; ссылки навигатора корректны | Проверка документации |

Проверки логики и CLI можно разместить в `tests/unit/bitrix24*.test.js` в текущем
проекте Jest `unit`; внешний транспорт подменять на границе API. CLI проверять
через запускаемую точку входа с контролируемыми зависимостями/окружением.
Не подменять поиск, пагинацию и сбор результата готовым успешным ответом.
Браузерный сценарий для CLI не нужен; существующие e2e обязательны как регрессия.

## План реализации

1. Перечитать `agents.md` и `docs/testing.md`, проверить рабочее дерево.
   Сохранить уже существующие изменения пользователя.
2. Подготовить `.env.example`, безопасное создание `.env` и правила `.gitignore`.
3. Реализовать чтение конфигурации, HTTP-клиент с безопасной обработкой ошибок,
   поиск метаданных и постраничное получение сделок.
4. Добавить CLI и npm-команду `bitrix:check` с оговорённым выводом.
5. Написать автоматические сценарии и выполнить затронутые проверки.
6. Дать пользователю путь к `.env`; после его заполнения выполнить живую
   проверку и сверку. Не читать секрет в вывод инструментов и не сохранять
   реальные ответы как fixtures. При недоступности портала явно отметить
   непроверенный К6 и причину.
7. Выполнить полный `npm test`, исправить обнаруженные регрессии.
8. После успешных обязательных проверок запустить субагента `docs-maintainer`
   по [правилам документации](../docs/documentation.md). Передать корень проекта,
   diff, поведение, результаты тестов и ограничения живой проверки.
   Дождаться результата, проверить `docs/` и ссылки корневого навигатора
   до сдачи, архивирования ТЗ или коммита.

## Проверка результата

Уже существующие команды:

```sh
npm ci
npm run test:install
npm run test:unit
npm run test:e2e
npm test
git diff --check
git status --short
```

Установка требуется только при отсутствии соответствующих зависимостей.
Правила и варианты запуска отдельных файлов — в [docs/testing.md](../docs/testing.md).

После реализации должна появиться новая команда `npm run bitrix:check`.
Для проверки исключения секретов использовать `git check-ignore -v .env .env.local`
и `git ls-files -- .env '.env.*'`: среди отслеживаемых файлов разрешён только
безопасный `.env.example`. Отдельно проверить, что пример не игнорируется.

Живая проверка требует предоставленного пользователем входящего вебхука,
доступного REST API портала, области `crm` и прав владельца вебхука на чтение
нужных сделок. Команда не может доказать отсутствие записей, скрытых правами.
В отчёте о реализации разделять результат автотестов и результат реального API;
не помещать туда секрет или полную выгрузку.

## Согласованные решения

- Пользователь ограничил текущий этап подключением API и проверкой данных:
  «пока что подключаем api и проверяем и ничего больше».
- Подтверждена локальная проверка в терминале без создания страницы сайта.
- Подтверждены `.env` вне Git и `.env.example` без секретного значения.
- Подтверждён поиск воронки, стадии, кодов полей и загрузка всех подходящих
  сделок; результат проверки — количество и несколько примеров.
- Имена полей, воронки и стадии заданы пользователем; отображаемая подпись суммы —
  `Ընդհանուր արժեք`.
- Подготовка этой постановки не включает реализацию или публикацию.
  Заполнение `.env` — внешняя зависимость живой проверки, а не открытый вопрос
  о требованиях.
