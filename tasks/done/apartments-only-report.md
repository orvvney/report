# Отчёт только по сделкам с типом недвижимости «Բնակարան»

Статус: готова к реализации

## Контекст и цель

Пользователь просит обновить график: получать поле `Անշարժ գույքի տեսակ`
и включать в отчёт только сделки со значением `Բնակարան` (квартира).
Сделки `Ավտոկայանատեղի` (парковка) исключаются.

Сейчас [getDeals](../src/bitrix24/deals.cjs) загружает все доступные сделки
воронки `Վաճառք`, стадии `Կնքված`, без ограничения по датам. Поле типа
недвижимости не запрашивается. [Агрегация](../src/report/aggregate.cjs)
строит два режима графика и общий список проблем по этой выборке.
Поэтому тип недвижимости сейчас не влияет на результат; это подтверждено кодом.
Количественное влияние на рабочий отчёт в рамках подготовки не измерялось.

## Подтверждённые данные интеграции

22 октября 2026 года выполнен запрос чтения `crm.item.fields` с
`entityTypeId: 2`, `useOriginalUfNames: 'N'` через настроенный серверный вебхук.
Найдено одно поле с точным заголовком `Անշարժ գույքի տեսակ`:

- Код: `ufCrm_1686472108`; исходное имя: `UF_CRM_1686472108`.
- Тип: `enumeration`; `isMultiple: false`; заполнение необязательно.
- `items` содержит пары `ID`/`VALUE`:

| ID на проверенном портале | VALUE |
| --- | --- |
| `541` | `Բնակարան` |
| `543` | `Թաունհաուս` |
| `545` | `Ավտոկայանատեղի` |
| `1405` | `Հասարակական տարածք` |

Эти коды — результат проверки метаданных, а не константы для реализации.
В текущем преобразовании метаданных `getDeals` сохраняет только `code`, `title`
и `type`, поэтому необходимые `items` и `isMultiple` потребуется сохранить.
Представление значения поля в реальных сделках отдельно не проверялось:
реализация должна корректно сопоставлять строковый и числовой ID элемента.
Секрет остаётся в существующей серверной настройке; в задачу и fixtures не переносится.

## Объём и требования

1. Дополнить получение данных отчёта полем `Անշարժ գույքի տեսակ`.
   Находить поле по точному заголовку, элемент списка — по точному `VALUE`
   `Բնակարան`; сравнивать значение сделки с найденным ID, а не с подписью.
2. Во всём отчёте, включая оба режима графика и список проблем, учитывать только квартиры. Пустое, отсутствующее,
   неизвестное значение и любой другой тип недвижимости исключаются.
   Не преобразовывать boolean, массивы или объекты в допустимый ID.
3. Отбор применять до вычисления сумм, количества, максимальной комнатности
   и формирования списка проблем.
   Например, парковка с комнатностью 20 не расширяет ось квартирного графика.
4. Сохранить отбор по воронке/стадии, полную пагинацию, режим имён `N`,
   правила проверки суммы, валюты, комнатности и даты для квартир.
   Комнатный график остаётся за всё время, месячный — за текущий год Еревана.
5. При отсутствии квартир возвращать существующее пустое представление отчёта:
   `rooms: []`, 12 месяцев с суммой `'0'` и количеством `0`, `problems: []`.
   Кнопка проблемных сделок не показывается.
6. Сохранить HTTP-контракт и состояния интерфейса из [docs/report.md](../docs/report.md).
   Отсутствие/неоднозначность нужного поля или элемента `Բնակարան`, несовместимые
   метаданные либо отказ чтения страницы должны давать существующий безопасный
   `502 {"error":"CRM_READ_ERROR"}`, без частичного отчёта и отката к полной выборке.
7. Отбор постоянный, применяется при открытии и ручном обновлении; новые элементы
   управления не требуются. Переключение режимов использует загруженный снимок.
8. Задача относится к отчёту. Диагностическая CLI `npm run bitrix:check`
   сохраняет прежний отбор всех сделок нужной воронки/стадии и прежний вывод.
   Расширение общего загрузчика не должно заставлять CLI зависеть от нового поля.

Сделки без значения `Բնակարան` полностью исключаются, даже если у них
некорректны сумма, валюта, комнатность или дата. Отсутствие типа недвижимости
само по себе не добавляет сделку в список проблем отчёта по квартирам.

## Критерии приёмки

- К1. Смешанная выборка квартир и других типов даёт в обоих графиках суммы
  и количество только квартир; ось комнатности определяется только квартирами.
- К2. Пустые, отсутствующие, неизвестные и некорректные значения типа не включаются;
  строковый и числовой ID нужного элемента дают одинаковый результат.
- К3. Без квартир графики показывают существующее пустое состояние и нулевые месяцы;
  список проблем пуст, его кнопка скрыта.
- К4. Динамически найденные код поля и ID элемента работают без привязки к `541`;
  ошибка метаданных или любой страницы даёт безопасную ошибку целого снимка.
- К5. Квартиры со старыми датами, неверной комнатностью, суммой или валютой
  обрабатываются по прежним правилам; обновление перечитывает тип недвижимости.
- К6. Сохраняются формат API, переключение без повторного чтения CRM и поведение CLI.
- К7. В общем списке проблем и его счётчике присутствуют только квартиры
  с ошибками существующих проверяемых полей. Остальные сделки не появляются
  в списке ни в одном режиме, независимо от ошибок их данных.

## План реализации

1. Прочитать [правила проекта](../agents.md), [описание отчёта](../docs/report.md)
   и [тестирование](../docs/testing.md).
2. В `src/bitrix24/deals.cjs` расширить путь загрузки для отчёта: разрешить
   запрос дополнительного поля с нужными метаданными и включить его код в `select`.
   Прежний вызов CLI должен оставаться совместимым. Сохранить получение всех страниц
   и текущую проверку структуры, фильтра и порядка ID.
3. В `src/report/load.cjs` задействовать расширенную загрузку. Разрешить ID квартиры
   по метаданным и применить отбор перед расчётами в `src/report/aggregate.cjs`
   либо отдельной чистой функции, вызываемой до агрегации. Не менять формат ответа.
   Отбор должен предшествовать также формированию списка проблем.
4. Расширить искусственные метаданные и сделки в `tests/support/crm-fixture.cjs`:
   базовые сделки существующих сценариев сделать квартирами; для новых сценариев
   явно задавать смешанные типы. Не копировать реальные сделки из CRM.
5. Добавить/обновить автоматические проверки ниже. Довести затронутые тесты,
   затем полный `npm test` до успешного завершения; исправить регрессии.
6. После реализации и успешных обязательных проверок запустить `docs-maintainer`
   по [docs/documentation.md](../docs/documentation.md), передать корень проекта,
   diff, новое поведение, результаты проверок и ограничения. Дождаться результата,
   проверить обновление `docs/` и ссылки корневого навигатора до сдачи,
   архивирования задачи или коммита. Подготовка этого ТЗ не запускает этот этап.

## Проверка результата

Команды подтверждены `package.json` и [docs/testing.md](../docs/testing.md):

```sh
npm run test:unit -- --runTestsByPath tests/unit/bitrix24.test.js tests/unit/report.test.js tests/unit/report-api.test.js
npm run test:e2e -- --runTestsByPath tests/e2e/report.test.js
npm test
git diff --check
```

E2e автоматически собирают приложение. При первичной установке нужны `npm ci`
и `npm run test:install`; Node.js 22.12.0+. Тесты не используют рабочий `.env`.
В sandbox может требоваться разрешение на запуск локального сервера/браузера.
Незавершённые или упавшие обязательные проверки явно сообщить пользователю;
такой результат не является успешной сдачей.

При подготовке ТЗ выполнялось только чтение кода и живых метаданных.
Функционал не изменён, автотесты в рамках подготовки не запускались.

## Согласованные решения

- В отчёт включать только `Բնակարան`; `Ավտոկայանատեղի` исключить.
- Пользователь подтвердил полное исключение всех сделок без `Բնակարան`
  из обоих графиков, списка проблем и связанных счётчиков. Пустые и остальные
  значения типа не дают оснований для включения в отчёт.
- Результат текущей работы — постановка задачи, без автоматической реализации.
